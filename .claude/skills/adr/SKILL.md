# adr

Цель — чтобы через неделю любой участник понял, **почему** сделано так, не спрашивая автора.

## Когда что

- **ADR** (`docs/adr/NNNN-<slug>.md`) — одно решение, 1 страница. Пример: «JSON IR вместо генерации Python-кода», «bpmn-auto-layout alpha вместо ELK».
- **RFC** (`docs/rfc/NNNN-<slug>.md`) — крупное предложение на обсуждение, несколько решений, диаграммы.

## ADR — шаблон

```markdown
# ADR-NNNN. <Решение в одной фразе>

- Статус: предложено | принято | заменено ADR-MMMM
- Дата: YYYY-MM-DD
- Связано: RFC-0001 §X, issue #N

## Контекст
Какая проблема, ограничения (сроки, VM 2 vCPU/4 ГБ, корпоративный контур, модели Яндекса).

## Варианты
| Вариант | Плюсы | Минусы |

## Решение
Что выбрали и почему — ссылаясь на факты (замеры, документацию), а не вкусы.

## Последствия
Что становится проще/сложнее, что надо сделать, когда пересмотреть.
```

## Шаги

1. Номер — следующий свободный в папке.
2. Пиши простым языком; термины — из `docs/glossary.md`, новые туда добавь.
3. Решение меняется → не переписывай старый ADR: новый ADR со статусом «принято», у старого — «заменено ADR-MMMM».
4. Обнови индекс `docs/README.md` (и таблицу решений в RFC, если есть).
5. Mermaid-диаграммы проверь на рендер (GitLab рендерит mermaid; избегай экспериментальных типов диаграмм).
