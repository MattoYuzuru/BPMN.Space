# cleaner

Основа — плагин `cleaner-agent` из https://github.com/MattoYuzuru/yuzuru-skills (marketplace `yuzuru-engineering`, подключён в `.claude/settings.json`). Если плагин установлен — используй его скиллы `cleaner-agent`, `cleanup-audit`, `documentation-reconciliation` как методику. Если нет — прочитай `plugins/cleaner-agent/skills/*/SKILL.md` и `references/` по ссылке и следуй тем же правилам:

- удаление только с доказательствами (прямые и косвенные ссылки, динамическая загрузка, сборка, деплой, тесты, история git); «поиск ничего не нашёл» — это зацепка, а не доказательство;
- решения и их обоснования не теряем: устаревший документ помечаем superseded, а не стираем;
- при расхождении документации и кода не считаем код заведомо правым — сверяем с RFC/ADR и тестами.

## Общие правила

- Работаем только в отдельной ветке `chore/cleaner-<light|hard>-<дата>` и только через MR.
- Чужие незакоммиченные изменения не трогаем.
- После правок — `make check`; перед MR — скилл `verify`.

## light

1. `ruff check --fix`, `ruff format`, `biome check --write`.
2. `vulture backend/app --min-confidence 80` и `knip` — кандидаты на удаление. Неиспользуемые импорты/переменные удаляй сразу; функции/файлы — только после проверки ссылок (роуты FastAPI, DI, Alembic, фикстуры pytest, entrypoints в compose — всё это «используется неявно»).
3. `make check`. Коммить только при зелёном результате.

## hard

1. Собери отчёты: `vulture`, `knip`, `jscpd --min-tokens 50 backend frontend/src`, `semgrep --config auto`, `pyright`, `pip-audit`, `npm audit --omit=dev`.
2. Составь план в MR-описании по шаблону `CLEANUP_PLAN.md` плагина: находка → доказательство → решение (оставить / исправить / объединить / удалить) → проверка.
3. Типовые исправления:
   - дубли конфигов → всё в `backend/app/config.py` / `.env.example`;
   - эндпоинты с почти одинаковой логикой → общий сервис в `services/`, роуты тонкие;
   - баги и уязвимости → тест, который падает, затем фикс;
   - нарушения слоёв (`domain` импортирует `infra`/`llm`) → перенос кода, `lint-imports` зелёный.
4. Сверка документации (методика `documentation-reconciliation`):
   - `make openapi` → `docs/api/openapi.json` и TS-клиент;
   - mermaid-диаграммы в `docs/architecture/` и RFC — модули, таблицы, эндпоинты совпадают с кодом;
   - `AGENTS.md`, `README.md`, `docs/README.md` — команды и пути реальные;
   - ADR не переписываем задним числом — при изменении решения новый ADR со ссылкой «supersedes».
5. Нетривиальные удаления покажи пользователю списком с доказательствами и дождись подтверждения.

## Итог

Отчитайся: что изменено, что удалено и как восстановить, какие проверки прошли, что осталось нерешённым. Не заявляй «код чистый» только потому, что инструменты ничего не нашли.
