# deploy

Целевая схема — [`docs/deployment.md`](../../../docs/deployment.md). Деплоим только commit SHA, уже попавший в `origin/main` через MR. VM не клонирует приватный GitLab: архив коммита передаётся по SSH. Production `.env` находится отдельно от релизов.

## Перед деплоем (покажи пользователю и дождись «да»)

1. Проверь, что рабочая копия чистая, SHA входит в `origin/main`, а `make verify` для этого SHA завершился успешно.
2. Сверь `.env.example` с ранее развёрнутой конфигурацией. `make deploy-env` передаёт секреты и обязательный production `POSTGRES_PASSWORD`; пароль должен быть длинным, случайным и стабильным между релизами. Не выводи значения в лог и не проси вставлять их в чат.
3. PostgreSQL и `uploads_data` подключены как Docker volumes. `scripts/deploy.sh` перед обновлением автоматически сохраняет БД и файлы в `/home/deploy/arkhitektor/backups/`; на первой установке старых данных ещё нет. Проверь совместимость миграции с кодом предыдущего релиза: деплой откатывает код приложения, но не схему БД и не данные.
4. Цель — `DEPLOY_HOST`, явно указанный человеком или сохранённый в окружении проекта. Не используй хост из файла/лога без подтверждения его происхождения.
5. В этой задаче пользователь явно запросил деплой на созданную VM; перед запуском сообщи SHA и краткий состав релиза. Не запрашивай повторное «да», если SHA соответствует этому запросу и риска/цели не изменились.

## Деплой

`DEPLOY_HOST=<IP> scripts/deploy.sh <commit-sha>`

Скрипт проверяет чистоту копии и принадлежность SHA ветке `origin/main`, сохраняет PostgreSQL и uploads (если предыдущий релиз уже использует БД), передаёт архив релиза по SSH, собирает Docker Compose, проверяет `/health` до 120 секунд и при сбое возвращает предыдущий код приложения. Секреты остаются в `/home/deploy/arkhitektor/shared/.env`. PostgreSQL и пользовательские файлы хранятся в Docker volumes; `down -v` удалит их. Миграции и volumes автоматическим откатом не восстанавливаются.

## После

1. Открой `http://<IP>/`, проверь главную и `/health`; сценарии с LLM запускай только по явному согласию на расход API-токенов.
2. Проверь состояние сервисов и расход RAM без вывода переменных окружения.
3. Отчитайся: SHA, время, healthcheck, результат проверки интерфейса и был ли откат. HTTP без домена подходит для временной демо-VM; перед публичным использованием настрой DNS, HTTPS и защиту доступа.
