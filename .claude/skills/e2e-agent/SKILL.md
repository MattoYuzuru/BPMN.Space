# e2e-agent

Дополняет скриптовый Playwright smoke (`make e2e`): агент проходит сценарий как человек и замечает то, что тест не ловит (кривая раскладка, непонятный текст вопроса, долгие ожидания).

## Подготовка

1. `docker compose up -d --wait`; убедись, что `GET /health` → 200.
2. LLM: провайдер задаётся окружением; по умолчанию `mock`. Для проверки только UI —
   `LLM_PROVIDER=mock` (записанные правила, без платных вызовов). Живой прогон из `.env`
   требует согласованного провайдера и бюджета, если пользователь ещё не разрешил его.
3. Входные данные — из `examples/` (текст регламента, голосовая заметка, документ). Не выдумывай новые персональные данные.

## Сценарий (RFC §2.1)

1. Создать проект.
2. Добавить источник-текст → запустить анализ → дождаться SSE `done`.
3. Проверить: вопросы появились, у каждого есть важность, цитата, допущение.
4. Ответить на один вопрос текстом, один — загрузкой аудио из `examples/`, один — проигнорировать.
5. Загрузить документ → новый прогон → плашка «решено / осталось / новые» соответствует ожиданию; у «решено» есть ссылка на источник.
6. «Построить» → схема отрисована, дорожки по ролям, есть XOR, элементы-допущения подсвечены.
7. Поправить схему мышкой (переименовать задачу, добавить задачу) → сохранить → появилась версия `manual`.
8. Скачать `.bpmn`; проверить XSD через `app.domain.bpmn.xsd.require_valid_bpmn` и
   bpmnlint через HTTP `/lint` запущенного `bpmn-tools` или его CLI из README.
   Цели `make validate` нет. Импорт/экспорт и токены настоящего canvas проверяет
   `make e2e-diagram`; для внешней проверки можно открыть https://demo.bpmn.io.

## Доказательства

Для каждого шага: скриншот, время ожидания, ошибки консоли браузера и логов backend (`docker compose logs backend --since 10m`). Итог — таблица «шаг → ✅/❌ → наблюдение» и список UX-замечаний отдельно от багов. Баги оформи как черновики issue (заголовок, шаги, ожидание/факт), но создавай их в GitLab только с подтверждения пользователя.
