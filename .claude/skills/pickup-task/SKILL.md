# pickup-task

Цель — чтобы любой участник (или его агент) за пару минут вошёл в чужую зону без устных объяснений.

## Шаги

1. **Источник задачи.** Если дан номер issue — прочитай его через GitLab API (скилл `gitlab-workflow`, если установлен; иначе `glab issue view N` или REST `GET /projects/:id/issues/:iid` с токеном из окружения). Сохрани: цель, критерии приёмки, метки `area::*`, `prio::*`, ссылки.
2. **Контекст документации** — читай только нужное:
   - `AGENTS.md` — карта репозитория и команды;
   - `docs/rfc/0001-architecture.md` — найди разделы по метке: `area::llm` → §5.1–5.4, §7; `area::backend` → §5.5–5.8; `area::frontend` → §2, §5.9; `area::devops` → §9–10;
   - `docs/adr/` — решения, которые задача может нарушить;
   - `docs/api/openapi.json`, если задача меняет API.
3. **Код.** Найди затронутые модули (поиск по именам из issue и RFC). Посмотри соседние тесты — они показывают принятый стиль.
4. **Ветка** от свежего `main`: `feature/<N>-<slug>`, `fix/<N>-<slug>` или `docs/<N>-<slug>`. В `main` напрямую не пушим — это запрещено правилами Codenrock.
5. **Короткий план** для пользователя: что меняем, какие файлы, какие тесты добавим, какие документы обновим. Если критерии приёмки неясны — спроси, не додумывай.

## Definition of Done (повтори пользователю)

- [ ] Тесты на новую логику; `make check` зелёный локально.
- [ ] Покрытие backend (`domain`, `services`, `ingest`) не ниже 80%.
- [ ] Поменялся контракт API → `make openapi` и перегенерирован TS-клиент.
- [ ] Поменялась архитектура → обновлены mermaid-диаграммы в `docs/architecture` или RFC.
- [ ] Принято неочевидное решение → ADR (скилл `adr`).
- [ ] `AGENTS.md` по-прежнему верен (новые команды, папки).
- [ ] MR с `Closes #N` и отчётом скилла `verify`.

Если нужной цели в `Makefile` ещё нет — не обходи проверку, а сообщи и предложи добавить её по RFC §9.
