# prompt-eval

Каноничные правила — `docs/backend/generation-quality.md`, пределы и приоритеты —
`docs/research/product-priorities-2026-10.md`. Полноценные `make eval`, `evals/` и
`make record-fixtures` пока не реализованы: не пытайтесь запускать их как существующие gates.

## Подготовка

1. Сформулируйте проверяемую гипотезу и выберите 2–3 случая, исходные материалы и ожидаемый граф.
2. Найдите соответствующую реализацию. Системные инструкции и few-shot находятся также прямо
   в `llm/{question_analysis,graph_generation,openai_compatible}.py`; отдельной папки `prompts/`
   сейчас нет. Не создавайте вторую копию правил без согласованного переноса.
3. Записанные сценарии `fixtures/ir/*.json` проходят адаптер, компилятор, XSD и реальный
   Node layout/lint в `make e2e-diagram`. Это проверка инфраструктуры и canvas, не оценка LLM.
4. Для живых вызовов согласуйте провайдера, объём и бюджет с пользователем, если это ещё не
   сделано в этой сессии. Секреты берите из защищённого окружения, не выводите и не коммитьте.

## Выполнение

- Материалы тура: `uv run --directory backend python scripts/tour_eval.py --runs 5`.
  По умолчанию mock; живая модель выбирается окружением. Скрипт проверяет стабильность
  учебного сценария, не качество всех бизнес-процессов.
- Сложные регламенты: три пары `fixtures/texts/{energy_incident,logistics_order,service_release}.md`
  и соответствующих `fixtures/ir/*.json`. `make dev-bpmn-tools` + `make eval-complex`
  запускают записанные правила на изолированном in-memory контейнере с настоящим layout/lint.
  Живой прогон явно включается: `uv run --directory backend python scripts/complex_eval.py
  --live --tools-url http://127.0.0.1:3000 --output ../reports/live-complex`.
  `--cases energy-incident logistics-order service-release` ограничивает выбранные случаи.
  Результаты, вопросы, XML/IR и точное сопоставление имён действий/ролей сохраняются даже при
  отказе. Это ограниченный набор, не общий `make eval`; связи и смысл оцениваются отдельно.
- Для смены модели — `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`,
  `LLM_JSON_MODE`, `LLM_JSON_MAX_TOKENS`; точный конфиг — `app/config.py` и `.env.example`.
  Переменной `LLM_OUTPUT_MODE` нет. Не меняйте production-конфиг в ходе сравнения.
- Сначала получите baseline, затем меняйте одну гипотезу за прогон. Сохраните SHA,
  модель/настройки, фактический ответ, вопросы, предупреждения, итоговые XML/IR, время,
  число запросов и токены. Денежную стоимость указывайте только по тарифу провайдера.

## Оценка

Сверяйте роли, действия, условия и связи с источником; сравнивайте по смыслу, а не только
по ID или точному названию. Отдельно учитывайте потерянные действия, выдуманные основания,
неподдерживаемую семантику, XSD/lint, repair и обрезку ответа. Проверьте фактические подписи
и видимость всей схемы в браузере. Число вопросов оценивайте относительно полноты материала.

Перед принятием изменения повторите затронутые записанные сценарии и обычный `make verify`.
Не заменяйте падение живого прогона успешной эталонной фикстурой. Отчёт должен явно разделять
качество модели, исправность компилятора/layout и непроверенные случаи.
