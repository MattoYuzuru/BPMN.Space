# ADR-0009. Удаление проекта, выход участника и сообщение об удалении

- Статус: принято в рабочей ветке; в production не развёрнуто
- Дата: 2026-10-07
- Расширяет правила удаления и членства [ADR-0001](0001-auth-and-project-sharing.md)

## Решение

| Кто вызывает `DELETE /projects/{id}` | Результат |
|---|---|
| Владелец | Удаляет проект, его источники, вопросы, версии, прогоны, вызовы модели, ссылки и членства |
| Принявший приглашение editor или viewer | Удаляет только своё членство; владелец и другие участники продолжают работать |
| Посторонний | 404; наличие частного проекта не раскрывается |
| Гость | 401 |
| Пользователь на демо-примере | 403; общий пример не удаляется |

`DELETE /projects/{id}/membership` — явный выход участника. Владелец получает 403: нельзя
случайно оставить проект без владельца. Удаление владельцем во время активного прогона — 409;
нужно сначала остановить прогон. Выход участника не отменяет общий прогон.

После удаления владельцем бывшие участники и обладатели действовавших ссылок получают 410:
`{"detail":"Автор удалил проект","code":"PROJECT_DELETED"}`. Остальные получают 404
(без аккаунта для частного адреса — 401). Отозванные и уже истёкшие на момент удаления ссылки
не получают новую информацию о проекте. Удаление из списка не оставляет доступ к источникам,
версиям или XML. UI сообщения подключает фронтенд по документированному машинному коду.

## Хранение и транзакции

Миграция `0012_deleted_project_access` добавляет таблицу квитанций:
`key_hash` (SHA-256, первичный ключ) и `expires_at` (индекс). Хеш идентифицирует пару
«проект + бывший пользователь» либо хеш действовавшей ссылки. Исходные идентификаторы,
почта, названия, документы и сырой токен в квитанцию не записываются.

Квитанция действует 30 дней (`DELETED_PROJECT_NOTICE_DAYS` в config.py); затем снова 404.
Просроченные записи очищаются при старте БД и при следующем удалении проекта. Это не архив,
корзина или восстановление удалённых данных. Удаление данных и запись квитанций — одна
транзакция; файлы удаляются после commit. Ошибка удаления файла журналируется и не откатывает
удаление БД. Если проект удалён во время загрузки, ещё не привязанный файл очищается;
отдельный reconciler оставшихся файлов пока не реализован.

Удаление, изменение состава участников, создание/отзыв ссылок и принятие приглашения
используют блокировку строки проекта. При принятии ссылка повторно проверяется под этой
блокировкой: удаление — 410, отзыв — 404, истечение — 410, без выдачи новых прав.
Собственное приглашение владельца не создаёт лишнее членство.

## Границы доступа

- Отзыв ссылки не отменяет уже принятое членство. Для полного отзыва нужно удалить участника
  и отключить доступные ему ссылки. Пока действующая ссылка существует, её можно принять снова.
- Выход участника не отзывает ссылку у остальных и допускает повторное принятие приглашения.
- Принятие viewer-ссылки не понижает существующего editor.
- Потеря доступа закрывает SSE перед следующим событием и WebSocket при периодической проверке
  (до 30 секунд). Все новые HTTP-запросы проверяют доступ сразу.
- Сообщения об удалениях, произошедших до этой миграции, восстановить нельзя: останется 404.
- Повторный выход — 404 после утраты членства; повторное удаление владельцем — 410 во время
  жизни квитанции, затем 404. Повтор не меняет данные других проектов.

## Проверки

HTTP-интеграционные тесты PostgreSQL: обе роли и оба адреса удаления; сохранность проекта
у других участников; каскад данных и удаление файла; приватность квитанций и истечение;
собственное приглашение; гонки удаления/отзыва/истечения с принятием; запрет удаления
во время прогона и допустимость выхода запустившего его участника.
