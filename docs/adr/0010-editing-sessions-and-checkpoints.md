# ADR-0010. Сессии правок и контрольные точки вместо версии на каждое автосохранение

- Статус: принято
- Дата: 2026-11-04
- Связано: [ADR-0003](0003-presence-and-version-history.md), [ADR-0004](0004-realtime-collaboration.md),
  [ADR-0007](0007-compact-version-storage.md), [RFC-0002](../rfc/0002-realtime-collaboration.md)
- Меняет решение ADR-0007: «группировать автосохранения» там отклонено, теперь принято

## Контекст

Каждое автосохранение (пауза 1,5 с после перетаскивания блока) создавало серверную версию. Номера
доходили до «Версия 347», после каждого сохранения появлялось уведомление «Схема сохранена», история
не отражала смысла: сотни почти одинаковых строк. ADR-0007 сжал XML (дельты BVD1), но отклонил
группировку автосохранений: «теряется точная история». Владелец продукта пересмотрел это
требование: точная посекундная история не нужна, нужны осмысленные точки и компактное хранение.

Замер размера строки ручной версии (оценка по фикстурам `app/fixtures/ir`, 25 элементов, цитата
~150 символов): сжатая дельта XML при перетаскивании — сотни байт; JSONB цитат (`trace`) — около
5 КБ несжатых, отчёт с допущениями (текст до 1000 символов на каждый элемент) — ещё 1-30 КБ.
`retain_trace` копировал все цитаты в каждую ручную версию. Метаданные занимали 80-95% строки,
поэтому одной дельты XML недостаточно. Замер не на боевой БД, а по структуре данных; порядок величин
подтверждает `test_sql_shares_unchanged_trace_and_report`: три правки подряд дают три строки с
пустыми `trace` и `report`.

## Решение

1. **Сессия правок.** Ручное сохранение вливается в последнюю версию, если одновременно:
   происхождение `manual`; тот же непустой `actor_email`; версия не контрольная точка; у неё нет
   зависимых (ни одна дельта не использует её базой, ни один прогон на неё не ссылается); последнее
   сохранение было менее `VERSION_SESSION_IDLE_SEC` назад (600), сессия началась менее
   `VERSION_SESSION_MAX_SEC` назад (3600). Иначе создаётся новая версия, как раньше. Сборка по
   источникам всегда создаёт новую версию и тем самым закрывает сессию; другой автор всегда начинает
   новую. Анонимные сохранения не сливаются: без `actor_email` разных людей не отличить.
2. **Слияние = замена строки.** В той же транзакции под блокировкой проекта строка головы
   удаляется, вставляется новая с **тем же номером и новым id**; дифф и дельта считаются от
   предшественника, `created_at` и `session_started_at` сохраняются, растёт `saved_count`,
   `updated_at` — время последнего сохранения. Новый id нужен, чтобы `base_version_id` других
   вкладок и соавторов честно устаревал (409 `stale_version`), как после обычной версии.
   Целостность ADR-0007 (SHA-256, глубина, база по номеру − 1) не нарушается: у удаляемой версии
   нет зависимых.
3. **Контрольная точка.** `POST /projects/{id}/versions/{version_id}/checkpoint` (`label` до 120
   символов, необязателен) закрепляет версию: `checkpoint = true`, сессия на ней закрыта. Операция
   идемпотентна. В интерфейсе это «Сохранить версию».
4. **Метаданные не копируются.** Если `trace` или `report` ручной версии равны метаданным
   предшественника, строка хранит `{}` и флаг `trace_inherited` / `report_inherited`; чтение
   берёт значение у ближайшей более старой строки-владельца. Счётчики `lint_count` и
   `assumption_count` хранятся отдельными колонками, чтобы список истории не читал JSONB.
5. **История страницами.** `GET /projects/{id}/versions?limit=30&before=N` возвращает
   `{items, next_before}`; строка без XML, цитат и отчёта (только счётчики). Список больше не
   восстанавливает XML и не запускает XSD на каждой версии: `xsd_valid` читается только в
   `GET /versions/{id}`. Одно сохранение проверяется XSD один раз и вне цикла событий.
6. **Интерфейс.** Нет уведомления о каждом автосохранении: в тулбаре постоянный индикатор
   «Сохраняется… / Сохранено / Не сохранено» с «Повторить». Тосты только для версии, собранной
   прогоном, ошибки сохранения, конфликта и явного «Сохранить версию». История группирует
   контрольные точки (с именем), сессии правок («Правки, 14:05–14:32», число автосохранений,
   автор) и сборки по источникам; страницы подгружаются при прокрутке (~90% списка), в шапке
   запрашиваются только 6 последних. Маркер «добавлено» сравнивается с ближайшей предыдущей
   контрольной точкой или сборкой, а не с номером − 1.

Миграция `0013_version_sessions` добавляет `label`, `checkpoint`, `session_started_at`,
`updated_at`, `saved_count`, `trace_inherited`, `report_inherited`, `lint_count`,
`assumption_count`; прежние версии становятся закрытыми одиночными сессиями, счётчики
заполняются из JSONB.

## Варианты

| Вариант | Последствия |
|---|---|
| Оставить версию на каждое сохранение, только скрыть тост | Номера и история по-прежнему шумят |
| Увеличить debounce | Больше потерь при закрытии вкладки, историю не исправляет |
| Обновлять строку головы на месте (тот же id) | Другие вкладки не заметят изменения: ломается `base_version_id` |
| Слияние заменой строки с новым id | Выбранный вариант |
| Отдельная таблица блобов метаданных по хэшу | Лишний слой и соединения; наследование от предшественника покрывает практический случай |

## Последствия

- Точная посекундная история ручных правок внутри сессии не хранится; хранится последнее
  состояние сессии. Версии до миграции не затронуты.
- Версия 2 до слияния и версия 2 после — разные id: ссылки на `/versions/{id}` из закладок на
  слитую версию перестанут работать (404). Публичных ссылок на конкретную версию нет.
- Откат релиза до `0013` безопасен: добавленные колонки удаляются, строки с наследованными
  `trace`/`report` теряют цитаты. Перед откатом выполните восстановление метаданных вручную
  или примите потерю цитат старых ручных версий.
- Восстановление версии (#30) и ревизии оснований (#34) по-прежнему не реализованы; контрольные
  точки — основа для них.
