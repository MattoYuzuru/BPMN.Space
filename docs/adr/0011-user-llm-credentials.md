# ADR-0011. Пользовательские ключи моделей и независимость от провайдера

- Статус: принято в рабочей ветке `feature/user-llm-providers`; в production не развёрнуто
- Дата: 2026-11-04
- Связано: RFC-0001 §5.1, [ADR-0001](0001-auth-and-project-sharing.md), [ADR-0008](0008-evidence-semantic-review-and-recovery.md)

## Контекст

Раньше backend строил один процессный `OpenAICompatiblePipeline` из `LLM_*` и отдавал его всем
пользователям. Один оператор платил за всех, модель менялась только перезапуском, а подключить
Anthropic или собственный ключ было нельзя. Запросы шли через `urllib` в потоках: отмена прогона
не прерывала оплаченный запрос и паузы между повторами, а общий пул потоков мог закончиться.

Цель владельца: каждый пользователь хранит свои ключи (Anthropic, OpenAI, любой совместимый
сервер), выбирает провайдера и модель, а прогоны и чат помощника работают при любом выборе.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Ключи только в окружении оператора | Просто, секреты вне БД | Один провайдер на всех, оператор платит за всех |
| Ключи в браузере (localStorage), запрос с ключом | Сервер ничего не хранит | Прогоны идут в фоне и переживают закрытие вкладки и рестарт; ключ уходит в каждый запрос |
| **Шифрованные ключи в БД, выбор на прогон** | Фоновые прогоны и восстановление после рестарта; ключ никогда не возвращается клиенту | Нужен серверный ключ шифрования и защита от SSRF |

## Решение

**Порт `LlmClient`** (`llm/client.py`): `complete(system, user, json_mode, max_tokens)`,
`list_models()`, `aclose()`. Адаптеры: `openai_compatible` (DeepSeek, OpenRouter, vLLM),
`openai` (`max_completion_tokens`, без `temperature` у рассуждающих моделей), `anthropic`
(официальный SDK). Пайплайн (`LlmPipeline`) не знает провайдера. Всё асинхронное: `httpx` и
`AsyncAnthropic`, паузы — `asyncio.sleep`, поэтому отмена прогона прерывает запрос. SDK Anthropic
работает с `max_retries=0`: повторы делает приложение, срок прогона сохраняется.

**Выбор модели** (`ModelResolver`) на каждый прогон и запрос помощника, по порядку:
явные `credential_id` + `model` в запросе → ключ пользователя по умолчанию → модель оператора
(`LLM_*`) → mock. В production без ключей mock не используется: ответ «Добавьте ключ модели
в настройках». Прогон, запущенный участником B, идёт на ключе B, а не владельца проекта.
Чужой `credential_id` неотличим от несуществующего (404).

**Хранение.** Таблица `user_llm_credentials` (миграция `0014`), ключ шифруется Fernet с серверным
`CREDENTIALS_ENCRYPTION_KEY` (список через запятую: первый шифрует, остальные расшифровывают —
ротация). В шифртекст зашит `user_id`: строку нельзя подменить другому пользователю. Без ключа
шифрования в production ключи не принимаются; в dev берётся временный ключ процесса с
предупреждением. Открытый ключ принимается один раз, проверяется запросом списка моделей и
никогда не возвращается API, не попадает в `llm_calls`, `runs.ir` и журналы (тексты ошибок
адаптеров не содержат тела и заголовков ответа, дополнительно работает `redact_secrets`).

**Прогон хранит** `model` и в `ir.execution` — `provider`, `credential_id`, но не ключ. После
рестарта ключ берётся заново по `credential_id` владельца запуска; удалённый или
нерасшифровываемый ключ — понятная ошибка, а не тихая подмена модели. `_check_recovered_input`
сравнивает provider и model.

**SSRF.** Адреса OpenAI и Anthropic фиксированы. Для совместимого провайдера пользователя: только
HTTPS без логина и параметров, имя хоста разрешается, а loopback, private, link-local (в том числе
метаданные облака), CGNAT, multicast и reserved отклоняются; проверка повторяется перед каждым
запросом, редиректы отключены. Локальный vLLM в dev разрешается явно через
`LLM_ALLOWED_PRIVATE_HOSTS`. Модель оператора из окружения доверенная и проверке не подлежит.

## Последствия

- `/me/llm-credentials` (список, создание, правка, удаление, `/{id}/models`); создание и список
  моделей идут через бюджет `expensive`.
- Интерфейс: `/settings` → «Модели и ключи», выбор модели в шапке проекта.
- DNS rebinding закрыт закреплением IP: транспорт `app/llm/pinned_transport.py` разрешает имя
  через `net_guard` в момент соединения и подключается к проверенному адресу, сохраняя имя в URL
  (Host, SNI и сертификат проверяются по имени). Прокси из окружения для таких клиентов отключены.
  Редиректы запрещены. Тело ответа ограничено `LLM_MAX_RESPONSE_BYTES` (8 МБ) для чата и `/models`.
- Структурные ответы Anthropic (`output_config.format`) не используются: анализ и граф
  описываются промптом и проверяются кодом (`generation-quality.md`).
- Пока нет `server-side-fallback` Anthropic и учёта стоимости токенов по ключам.
- Ключи не передаются между пользователями и проектами; общий ключ команды не предусмотрен.
- Конфигурация: `CREDENTIALS_ENCRYPTION_KEY`, `LLM_ALLOWED_PRIVATE_HOSTS`, `LLM_ANTHROPIC_EFFORT`,
  `LLM_MODELS_CACHE_SEC`, `LLM_MAX_RESPONSE_BYTES`. Старые `DEEPSEEK_*` действуют только если не задан одноимённый `LLM_*`,
  о них пишется предупреждение. Production не стартует с `STT_PROVIDER=mock`, а при
  `LLM_PROVIDER=mock` требует `CREDENTIALS_ENCRYPTION_KEY`; демо-данные в production по умолчанию
  не засеваются.
