# Агентный режим: модель читает источники инструментами (RFC-0004)

Обычный прогон — фиксированный конвейер: код решает, какая порция источников и в каком порядке
уйдёт модели. Агентный режим даёт модели инструменты только-чтения и бюджет: она сама решает,
какие разделы читать и что искать, но **сервер по-прежнему проверяет каждое утверждение**.
Проект меняется только после `submit`, который проходит те же проверки, что конвейер.

Каноничные правила качества — [generation-quality.md](generation-quality.md#агентный-режим-rfc-0004),
решение и границы — [RFC-0004](../rfc/0004-agent-mode.md), бюджет и профиль —
[RFC-0005](../rfc/0005-full-model-capacity-and-cost.md).

## Как включить

1. **Модель с инструментами.** Подойдёт Claude 5.5 (`capabilities.tools` из справочника
   возможностей) и модели OpenAI с поддержкой tools. У mock-модели инструментов нет: агентный
   режим на ней недоступен.
2. **Флаг оператора.** `LLM_AGENT_MODE=true` в окружении backend (по умолчанию `false`).
   Флаг один на сервер: включение режима — осознанное решение оператора, а не пользователя.
3. **Профиль прогона.** `POST /api/v1/projects/{id}/runs`:

```json
{
  "mode": "build",
  "profile": {
    "mode": "agent",
    "max_steps": 12,
    "effort": "high",
    "budget": {"tokens": 400000, "cost_usd": 10}
  }
}
```

   `mode` в профиле: `pipeline` (по умолчанию) или `agent`. `max_steps` — лимит ходов, только
   вместе с `mode=agent`, не больше серверного `LLM_AGENT_MAX_STEPS`. Ответ `422` с понятным
   текстом, если режим выключен оператором, модель не умеет инструменты, `max_steps` задан без
   агентного режима или превышает серверный потолок.
4. **Оценка до запуска.** `POST /api/v1/projects/{id}/runs/estimate` с тем же профилем отдаёт
   диапазон: нижняя граница — «оглавление и submit», верхняя — лимит ходов и бюджет. Оценка
   помечена приблизительной: путь чтения выбирает модель.

MCP (`RFC-0007`) агентный режим пока не выставляет: `_profile_json` в `app/mcp/tools.py`
принимает только `effort` и `semantic_review`, внешний агент не может ни включить режим, ни
задать его бюджет.

## Что делает агент

Стартовое сообщение содержит оглавление источников (id, название, тип, объём, полнота чтения),
число и коды существующих вопросов, размер текущей схемы, остаток ходов и бюджет, а также
JSON Schema IR. Дальше модель сама вызывает инструменты:

| Инструмент | Что возвращает | Проверка/лимит сервера |
|---|---|---|
| `list_sources()` | id, название, тип, объём, предупреждения чтения | только источники проекта |
| `read_source(source_id, from, limit)` | фрагмент текста, границы, `next_from` | не больше `LLM_AGENT_READ_MAX_CHARS` за вызов; `from` за концом текста — ошибка |
| `search_sources(query)` | фрагменты с совпадениями и id источника | PostgreSQL FTS `russian`; только активные готовые источники с текстом, без кратких содержаний и навигационных производных (`frames`, `media_feed`); только источники снимка прогона; лимит `LLM_AGENT_SEARCH_LIMIT` |
| `list_questions()` | коды, статусы, виды, тексты и допущения бизнес-вопросов | технические вопросы не показываются |
| `propose_question(text, assumption, quotes[])` | `P-N` — черновик без сохранения | каждая цитата дословна и из доступного источника |
| `check_graph(ir)` | `ok` или адресные ошибки | схема IR, ручные правки, основания, топология, XSD, `bpmnlint`; ничего не сохраняет |
| `submit(questions, ir)` | принято или ошибки | те же проверки; публикация обычными этапами прогона |

`propose_question` — черновик: `submit` принимает и полный вопрос, и ссылку
`{"proposal_id": "P-1"}`. Вопросы без дословных цитат отклоняются до сохранения; дубликаты
существующих вопросов не создаются. `assumption_of` в IR ссылается только на существующие
OPEN/IGNORED вопросы — новое предложение нельзя использовать как допущение в этом же прогоне.

`list_questions` показывает и тексты ответов аналитика (до 500 знаков): по ним видно, что уже
решено. `search_sources` индексирует название и первые 100 тыс. знаков текста — это предел
`tsvector` PostgreSQL; хвост длинного документа агент читает через `read_source`. Навигационные
производные записи («общая лента», «ключевые кадры») в поиск не попадают: они дублируют
расшифровку и описание экрана, а читать их как источник нельзя. Поиск идёт по текущей базе, но
выдача фильтруется по снимку прогона: источник, добавленный после старта, модели не подсунут.

После `submit` работают обычные этапы: сверка вопросов со снимком знаний (под блокировками),
проверка цитат, `add_version`, раскладка `bpmn-tools`. Если материалы изменились во время
прогона, прогон завершается понятной ошибкой, а не публикует устаревший результат.

## Бюджет и ожидание пользователя

Перед каждым ходом проверяются: число ходов, суммарные токены и деньги прогона (включая
потраченное до продолжения после `waiting`). Достигнутая граница — **не ошибка**: прогон
переходит в `waiting`, создаётся блокирующий технический вопрос `budget_reached`.

- **Исчерпан бюджет токенов или денег** — действия «поднять бюджет» и «открыть настройки».
  «Поднять бюджет» повышает только границы профиля; продолжение — новая попытка, а потраченные
  токены и деньги по-прежнему считаются по журналу `llm_calls`.
- **Исчерпан лимит ходов** — бюджет к этой границе отношения не имеет, поэтому действий «поднять
  бюджет» нет: предлагаются «продолжить с новым запасом ходов» (новая попытка с полным
  `max_steps` из профиля; потраченные ходы прошлой попытки её не уменьшают) и «открыть
  настройки». Чтобы поднять сам предел, нужен новый прогон с большим `max_steps` —
  серверный потолок задаёт `LLM_AGENT_MAX_STEPS`.

`POST /runs/{id}/resume` или действие вопроса продолжают прогон. Отмена прерывает текущий
HTTP-запрос и цикл между ходами; уже оплаченный ход при этом попадает в журнал (см. ниже).

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `LLM_AGENT_MODE` | `false` | оператор включает агентный режим |
| `LLM_AGENT_MAX_STEPS` | `24` | серверный потолок ходов на прогон |
| `LLM_AGENT_READ_MAX_CHARS` | `12000` | максимум символов за `read_source` |
| `LLM_AGENT_SEARCH_LIMIT` | `5` | совпадений в `search_sources` |
| `LLM_AGENT_SEARCH_SNIPPET_CHARS` | `400` | длина фрагмента в выдаче поиска |
| `LLM_AGENT_MODE` + `RunProfile.budget` | — | токены и деньги: мягкая остановка |

## Журнал и стоимость

Один **оплаченный** ход модели — один ряд `llm_calls` с `stage=agent`: номер хода, имена
инструментов, SHA-256 аргументов и результатов, токены, кеш, стоимость по ценам на момент
вызова, дата цен и короткий класс сбоя. Ход записывается даже тогда, когда ответ модели не
дошёл до инструментов: текстовый ответ без вызова инструмента, обрезка по `max_tokens`, отказ
модели, сбой инструмента или отмена — иначе бюджет, стоимость и счётчик ходов после рестарта
занижались бы. Запись идёт в `finally` и доводится до конца при отмене.

Тексты источников в журнал не копируются. `GET /runs/{id}` и SSE-событие `usage` показывают
потраченное с разбивкой по этапам; подпись этапа в `by_stage` — «Агентное чтение». Цитаты и
граф лежат там же, где у конвейера (`runs.ir`, `versions`), поэтому аудит не зависит от режима.

## Восстановление после рестарта (ADR-0008)

В `ir.execution.agent` сохраняются число оплаченных ходов, журнал хешей и принятый `submit`
(вопросы и канонический IR):

- **`submit` был принят.** После рестарта вопросы и граф перепроверяются по текущим источникам и
  вопросам и публикуются без повторной оплаты; затем черновик ещё раз проверяется на этапе
  структуры — после сверки вопросов, — чтобы не опубликовать схему, устаревшую относительно
  новых вопросов или ручных правок. Если проверка не проходит, прогон завершается ошибкой
  «сданный результат не прошёл повторную проверку», а не публикует устаревшее.
- **Флаг оператора и возможности модели перепроверяются.** Восстановленный агентный прогон
  останавливается понятной ошибкой, если `LLM_AGENT_MODE` выключили или у модели больше нет
  инструментов: тихой подмены режима на конвейер нет.
- **Цикл не завершён.** Продолжение идёт с сохранённым счётчиком ходов: рестарт не обнуляет
  лимит. Потраченные токены и деньги входят в бюджет через журнал `llm_calls`.
- **Сменилась версия промпта** (`AGENT_PROMPT_VERSION`): сданный результат не переиспользуется,
  цикл выполняется заново с новыми правилами; счётчик ходов сохраняется.

## Живая проверка перед включением

Записанные ответы проверяют механику, но не транспорт провайдера. У Claude 5.5 рассуждение
включено всегда, и API требует возвращать блоки `thinking`/`redacted_thinking` с подписью в
истории цикла инструментов — адаптер хранит сырые блоки ответа (`ToolTurn.provider_blocks`) и
возвращает их в следующем запросе. Перед включением `LLM_AGENT_MODE` на стенде нужен живой
прогон: два-три хода с инструментами на реальном ключе (проверить отсутствие 400 про thinking и
корректность расхода). Живой прогон в этот шаг не входит — только записанные сценарии.

## Как проверять без сети

Тесты — `backend/tests/test_agent_mode.py` (цикл и инструменты на записанных
`tool_use`/`tool_calls`, бюджет, отмена, восстановление, in-memory поиск) и
`backend/tests/test_agent_search_pg.py` (FTS `russian` и миграция `0024` на PostgreSQL).
Записанный клиент — `app/llm/mock.py:RecordedToolClient`; живой провайдер не нужен.

```sh
cd backend
uv run pytest tests/test_agent_mode.py tests/test_agent_search_pg.py -q
uv run pytest tests/test_agent_search_pg.py -q   # с TEST_DATABASE_URL=…:5433
```

## Ограничения и что дальше

- Нет `worker`/`delegate` и дешёвых рабочих моделей (RFC-0006, шаги 4–5): все ходы идут на
  модели прогона.
- Нет MCP-доступа к режиму, кеша производных источников и кеша ответов инструментов, живого
  прогресса ходов в SSE, смысловой сверки после `submit` и эталонного сравнения с конвейером на
  живых моделях (механика тестов есть, живой замер — на `prompt-eval`).
- Инструменты не видят нераспознанные сканы, веб-страницы, кадры видео и записи без текста:
  это следующие шаги RFC-0006.
- Поддержан BPMN шире IR v1 не становится: ограничения те же, что у конвейера
  (`generation-quality.md`).
