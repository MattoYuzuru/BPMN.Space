# Аккаунты и общий доступ к проектам

Backend предоставляет email/password аккаунты, серверную cookie-сессию и доступ к проекту по ролям. Требуется PostgreSQL и миграция `0005_auth_and_sharing`; в примере окружения `AUTH_ENABLED=true`.

## Сессия

1. Получить `GET /api/v1/auth/csrf`; сохранить cookie `arkhitektor_csrf` и значение `csrf_token`.
2. Для регистрации отправить JSON на `POST /api/v1/auth/register` с `email` и паролем не короче 12 символов.
3. Для входа отправить `application/x-www-form-urlencoded` на `POST /api/v1/auth/session/login`: поле `username` содержит email, поле `password` — пароль.
4. Добавлять значение CSRF cookie в `X-CSRF-Token` каждого изменяющего запроса. Сессионная cookie называется `arkhitektor_session`, HttpOnly, действует 14 дней; `GET /api/v1/auth/me` возвращает текущий профиль, `POST /api/v1/auth/session/logout` завершает сессию.

Сессионный токен в PostgreSQL хранится только в виде SHA-256 хеша. Пароль хешируется Argon2 библиотекой FastAPI Users. В production `APP_ENV=production` включает `Secure` у cookie, поэтому сайт должен быть доступен по HTTPS.

## Роли и приглашения

Создавать проект может только вошедший пользователь. Доступ имеют владелец и добавленные редакторы. Любой пользователь, который вошёл в систему, может просматривать демонстрационные проекты в режиме чтения.

Владелец создаёт ссылку через `POST /api/v1/projects/{project_id}/share-links`:

```json
{
  "role": "viewer",
  "expires_in_days": 30
}
```

`role` принимает `viewer` или `editor`; `expires_in_days` необязателен, диапазон — 1–365. Ответ содержит путь `/share/<token>` только при создании. Секретная часть не отображается в списке ссылок и не хранится в базе открыто.

- `viewer`: ссылка сразу разрешает открыть данные проекта и скачать версии BPMN через `/api/v1/shares/{token}` и `/api/v1/shares/{token}/versions/{version_id}/xml`; изменять данные нельзя.
- `editor`: пользователь должен войти или зарегистрироваться и выполнить `POST /api/v1/shares/{token}/accept`. После принятия его аккаунт становится редактором проекта.
- Владелец управляет ссылками через `GET`/`DELETE /api/v1/projects/{project_id}/share-links[/{link_id}]`, а редакторами — через `GET`/`DELETE /api/v1/projects/{project_id}/members[/{user_id}]`.
- Отзыв ссылки закрывает приглашение, но не удаляет уже принятого редактора; его доступ отзывается отдельно через `/members/{user_id}`.

Неизвестная или отозванная ссылка отвечает `404`, истёкшая — `410`. Ответы редакторской ссылки без сессии — `401`; просмотр по ссылке не открывает проект в общем каталоге.

Ссылку с ролью следует считать секретом уровня пароля: передавайте её только нужным людям и не вставляйте в публичные issue или логи.

## Действия перед включением на существующей VM

1. Сделать резервную копию PostgreSQL и пользовательских файлов.
2. Сопоставить существующие приватные проекты с владельцами; выполнить backfill `projects.owner_id` для нужных строк. Миграция намеренно не назначает их первому зарегистрированному пользователю и не делает публичными.
3. Проверить, что backend доступен по HTTPS, а `APP_ENV=production` задан в секретном `.env`.
4. Применить миграцию и только затем включать `AUTH_ENABLED=true`.
5. Пока интерфейс входа и управления ссылками не подключён на frontend, текущий клиент не сможет создавать проекты при включённой авторизации. На этой ветке реализован backend-контракт; UI-интеграция — отдельный этап.

Подтверждение email, восстановление пароля и лимитирование попыток входа пока не настроены. Для релиза за пределы закрытого стенда нужны email-провайдер и инфраструктурное ограничение попыток входа.
