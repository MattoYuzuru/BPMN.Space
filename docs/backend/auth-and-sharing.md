# Аккаунты и общий доступ к проектам

Backend предоставляет email/password аккаунты, серверную cookie-сессию и доступ к проекту по ролям. Требуется PostgreSQL и миграции до `0012_deleted_project_access`; в примере окружения `AUTH_ENABLED=true`. Решения — [ADR-0001](../adr/0001-auth-and-project-sharing.md) и [ADR-0002](../adr/0002-rate-limits-and-secure-cookies.md).

## Кто что видит

При `AUTH_ENABLED=true` весь API требует входа (`401` для гостя), кроме:

- `/auth/*` (регистрация, вход, CSRF, состояние сессии);
- `GET /examples` и `/health`;
- `/shares/{token}` и `/shares/{token}/versions/{id}/xml`: ссылка `viewer` работает без входа.

Вошедший пользователь видит свои проекты, принятые общие проекты (с ролью редактора или наблюдателя) и демо-проекты из сида (только чтение). Чужой проект отвечает `404`, а не `403`, чтобы не раскрывать его существование. Без PostgreSQL при включённой auth ответ `503`.

| Действие | owner | editor | viewer (демо или принятая ссылка) |
|---|---|---|---|
| Читать проект, источники, вопросы, версии, XML | да | да | да |
| Переименовать проект, менять источники, отвечать на вопросы, запускать прогоны, сохранять схему | да | да | `403` |
| Удалить проект | да | `403` | `403` |
| Ссылки доступа и участники | да | `403` | `403` |

Гость читает проект по действующей `viewer`-ссылке через `/shares/{token}`. После принятия ссылки в аккаунт наблюдатель может читать проект через обычные маршруты, но не менять его. Помощник (`/assistant/chat`, `/projects/{id}/assistant`) и `POST /transcriptions` требуют аккаунта: за ними платные провайдеры.

## Область списка проектов

`GET /api/v1/projects?scope=…` сужает выдачу при включённых аккаунтах (без них параметр не действует):

| `scope` | Что вернёт |
|---|---|
| `all` (по умолчанию) | всё доступное: свои, принятые общие проекты, демо-примеры |
| `own` | проекты, где вы владелец |
| `shared` | проекты, доступ к которым вы приняли по ссылке (viewer или editor) |
| `examples` | демо-примеры из сида (только чтение) |

Поиск `q`, курсор и `total` работают поверх области: `total` считается по ней же. Неизвестное значение — `422`. Фильтр в SQL — `SqlProjectRepository._visible_to(user_id, scope)`, в памяти (без PostgreSQL) область `shared` пуста.

## Сессия

1. `GET /api/v1/auth/session` отвечает всегда `200`: `{"auth_enabled": bool, "user": {"id", "email"} | null}`. По нему клиент решает, показывать ли вход. `GET /auth/me` для гостя отвечает `401`.
2. Получить `GET /api/v1/auth/csrf`; сохранить cookie `arkhitektor_csrf` и значение `csrf_token`.
3. Регистрация: JSON на `POST /api/v1/auth/register` с `email` и паролем не короче 8 символов.
4. Вход: `application/x-www-form-urlencoded` на `POST /api/v1/auth/session/login`, поле `username` содержит email, `password` — пароль. Успех — `204` и cookie `arkhitektor_session`.
5. Каждый изменяющий запрос (включая регистрацию и вход) несёт значение CSRF cookie в заголовке `X-CSRF-Token`, иначе `403`. Выход — `POST /api/v1/auth/session/logout`. Запросы с `Authorization: Bearer` (токен доступа, см. ниже) без cookie-сессии CSRF не требуют.

Ошибки аккаунтов (`detail` у входа и регистрации — код FastAPI Users, а не русский текст; клиент сопоставляет его со своим сообщением):

| Запрос | Статус | `detail` |
|---|---|---|
| вход с неверной парой | `400` | `LOGIN_BAD_CREDENTIALS` |
| повторная регистрация | `400` | `REGISTER_USER_ALREADY_EXISTS` |
| пароль короче 8 или кривой email | `422` | русское сообщение вида «Некорректный запрос: «password» — слишком короткое значение» |
| нет или не совпал CSRF | `403` | «CSRF-токен отсутствует или не совпадает» |

Сессия — случайный токен, в БД хранится только его SHA-256, срок 14 дней. Пароль хешируется Argon2. Cookie `HttpOnly`, `SameSite=Lax`; флаг `Secure` включается автоматически при `APP_ENV=production` (или `prod`) и переопределяется `SESSION_COOKIE_SECURE`. Production требует HTTPS для входа: сайт с `Secure` по обычному HTTP не сохранит cookie. На стенде без HTTPS задайте `SESSION_COOKIE_SECURE=false` в серверном окружении. Пустое значение переменной считается «не задано», тогда решает `APP_ENV`.

## Ссылки и приглашения

Владелец создаёт ссылку через `POST /api/v1/projects/{project_id}/share-links`:

```json
{ "role": "viewer", "expires_in_days": 30 }
```

Обе роли предлагают одинаковые сроки: `7`, `30`, `365` дней (год) и `0` (бессрочно). Если
`expires_in_days` не передан, срок по умолчанию — 30 дней. Бессрочная ссылка хранится как
`expires_at = null`; владелец в любой момент может отозвать её.

| Роль | По умолчанию | Доступные варианты |
|---|---|---|
| `editor` | 30 дней | 7 дней, 30 дней, год, бессрочно |
| `viewer` | 30 дней | 7 дней, 30 дней, год, бессрочно |

Срок больше года — `422`. Ответ содержит путь `/share/<token>` только при создании; в списке ссылок и в БД секрета нет.

- `viewer`: ссылка разрешает открыть проект и скачать версии BPMN через `/api/v1/shares/{token}` и `/shares/{token}/versions/{version_id}/xml` без входа. Вошедший пользователь может выполнить `POST /api/v1/shares/{token}/accept`, после чего проект попадёт в его профиль; менять данные нельзя.
- `editor`: пользователь входит или регистрируется и выполняет тот же `POST /api/v1/shares/{token}/accept`. После этого он редактор проекта (членство хранится в БД и не зависит от срока ссылки).
- Принятое членство сохраняется после истечения или отзыва ссылки. Владелец отзывает доступ через `/members/{user_id}`; принятие viewer-ссылки не понижает уже выданную роль editor.
- Владелец управляет ссылками (`GET`/`POST`/`DELETE /projects/{id}/share-links[/{link_id}]`) и участниками (`GET`/`DELETE /projects/{id}/members[/{user_id}]`). Отзыв ссылки не удаляет принятое членство: участника убирают отдельно через `/members/{user_id}`.

Неизвестная или отозванная ссылка отвечает `404`, истёкшая — `410`. Ссылка редактора без сессии — `401`. Ссылку нужно считать секретом уровня пароля: не вставляйте её в публичные issue и логи.

## Токены доступа для агентов

Шаг 1 [RFC-0007](../rfc/0007-external-agents-mcp.md): персональный токен даёт внешнему агенту
(Claude Code, Claude Desktop, скрипт) доступ к REST API `/api/v1` от имени пользователя, но
только в пределах выбранных прав и проектов. MCP-сервер (`/mcp`) — следующий шаг; команда
подключения в интерфейсе уже показывает его адрес.

**Создание и хранение.** Настройки → «Доступ для агентов» или `POST /api/v1/me/api-tokens`
(только cookie-сессия, с CSRF):

```json
{ "name": "Claude Code на ноутбуке", "scopes": ["projects:read", "questions:answer"],
  "project_ids": null, "expires_in_days": 30 }
```

Ответ `201` содержит `secret` вида `bps_<43 символа>` **один раз**; в списке
(`GET /me/api-tokens`) и в БД его нет — только SHA-256 и префикс `bps_xxxxxx` для опознания.
`scopes` по умолчанию — чтение и ответы; `project_ids: null` — все проекты пользователя, включая
будущие; в списке — только доступные пользователю проекты (иначе `404`), до 100. Срок обязателен:
1–365 дней, по умолчанию 30, бессрочных токенов нет. Действующих токенов — не больше 50 (`409`).
`DELETE /me/api-tokens/{id}` отзывает токен мгновенно; отозванные из списка пропадают,
истёкшие остаются с `expired: true`.

**Вход.** Заголовок `Authorization: Bearer bps_…` в любом маршруте `/api/v1`. Пользователь —
владелец токена; cookie при этом не читается (неверный токен рядом с действующей cookie — всё
равно `401`). CSRF не проверяется, только если в запросе есть Bearer и **нет** cookie-сессии:
чужой сайт не может добавить этот заголовок без CORS-preflight. С cookie-сессией CSRF нужен как
обычно. Вход, регистрация и выход (`/auth/session/*`, `/auth/register`) с любым заголовком
`Authorization` отклоняются (`403`): эти маршруты FastAPI Users читают только cookie.
Неизвестный, отозванный, истёкший токен и токен заблокированного аккаунта — одинаковый `401`
«Токен доступа недействителен…» на любом маршруте: владелец проверяется раньше права маршрута.
`last_used_at` пишется не чаще раза в минуту.
SSE прогона принимает токен и закрывается после отзыва так же, как после выхода; WebSocket
комнаты и presence по токену недоступны.

**Права.** Токен сужает, но не расширяет роль: наблюдатель с `projects:write` всё равно получает
`403` «нужны права редактора», проект вне `project_ids` — `404`, как чужой.

| Право | Маршруты |
|---|---|
| `projects:read` | `GET /projects` (с ограничением проектами список и `total` сужаются), `GET /projects/{id}`, вопросы, версии и XML, `GET /runs/{id}`, `GET /runs/{id}/events`, оценка прогона `POST /projects/{id}/runs/estimate` (бесплатная, только `count_tokens`) |
| `projects:write` | `POST /projects`, `POST /projects/from-example` (только токен без ограничения проектами), `PATCH /projects/{id}`, `PUT /projects/{id}/diagram`, контрольная точка версии |
| `sources:write` | `POST /projects/{id}/sources/{text,file,sample}`, `PATCH /sources/{id}`; загрузка аудио или видео в `sources/file` — ещё и `runs:start` (запись расшифровывает платный провайдер) |
| `sources:delete` | `DELETE /sources/{id}` |
| `runs:start` | `POST /projects/{id}/runs`, `POST /runs/{id}/cancel`, `POST /runs/{id}/resume`, помощник (`/projects/{id}/assistant`, `/assistant/chat`), `POST /transcriptions` — платные вызовы на ключах владельца |
| `questions:answer` | `POST /questions/{id}/{answer,ignore,reopen}` |
| любой действующий токен | `GET /auth/me`, `GET /auth/session` |

Нехватка права — `403` с названием нужного права, например «Токену не хватает права
«sources:write» (добавлять и изменять источники)…».

**Что через токен нельзя** (`403` «Это действие недоступно по токену доступа…»): управлять
токенами, ключами моделей (`/me/llm-credentials`), ссылками доступа и участниками, принимать
ссылки, удалять проект или выходить из него, онбординг, билеты комнаты и presence. Вход,
регистрация и выход работают только через cookie. Маршрут закрыт по умолчанию: открыт только тот,
у которого объявлено право `require_scope(...)` в декораторе (или `APIRouter(dependencies=…)`;
пометка в `include_router(dependencies=…)` не учитывается) — `app/api/access.py`. Проверяет его
аутентификация по токену (`services/auth.token_user`) по дереву зависимостей маршрута. Право,
зависящее от тела запроса (медиафайл), проверяет `require_token_scope` в обработчике. Перечень
открытых маршрутов и то, что пользователь везде определяется через `optional_user`/`stream_user`,
зафиксированы в `tests/test_api_tokens.py`.

Пример (секрет — из окна создания; в репозиторий и логи его не кладите):

```bash
curl -s https://example.org/api/v1/projects -H "Authorization: Bearer $BPS_TOKEN"
curl -s -X POST https://example.org/api/v1/questions/QUESTION_ID/answer \
  -H "Authorization: Bearer $BPS_TOKEN" -H "Content-Type: application/json" \
  -d '{"text": "Согласует начальник отдела"}'
```

Пока нет (следующие шаги RFC-0007): MCP-сервер, пометка «через агента» у ответов и источников,
журнал действий агента в проекте, отдельный от аккаунта бюджет `expensive` на токен.

## Долгоживущие соединения

WebSocket комнаты открывается по одноразовому билету с TTL 60 секунд и проверенным Origin. Для
аккаунтного билета нужна действующая cookie-сессия того же пользователя: другой аккаунт или
отсутствующая cookie не позволяют использовать билет. Каждые 30 секунд сервер повторяет проверку
сессии и роли; после выхода, истечения сессии, блокировки аккаунта или отзыва членства закрывает
соединение с кодом `1008`. Гостевой viewer-билет проверяет действующую ссылку; отзыв ссылки закрывает
гостевую комнату, а принятое членство сохраняется по правилам выше.

Presence SSE и SSE прогона проверяют текущую cookie и права перед каждым событием, включая историю
прогона и события, уже находящиеся в очереди. При отсутствии событий проверка выполняется каждые
30 секунд. Поток закрывается без следующего события при потере доступа, pending-подписка очищается.
Проверки используют короткие сессии PostgreSQL и не удерживают соединение БД на всё время потока.

## Скачивание XML

`GET /versions/{id}/xml` и `GET /shares/{token}/versions/{id}/xml` отдают файл вложением и запрещают браузеру открывать его как страницу:

```
Content-Disposition: attachment; filename="diagram-v3.bpmn"
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; sandbox
```

При ручном сохранении схемы (`PUT /projects/{id}/diagram`) XML проверяется: допускаются только пространства имён BPMN 2.0 (model, BPMNDI, DC, DI), цвета bpmn-js (`color`, `biocolor`) и `xsi`. Отклоняются (`422`, русское сообщение) DTD и сущности, инструкции обработки, любые другие элементы и атрибуты — в том числе `<script>` из XHTML/SVG. Штатный `bpmn:script` у `scriptTask` разрешён: браузер его не исполняет.

## Лимиты частоты

Защита от спама, а не свойство продукта; значения щедрые, настраиваются через `RATE_LIMIT_*` (см. `.env.example`). При превышении `429`, заголовок `Retry-After` (секунды), `detail`: «Слишком много запросов. Повторите через N с.».

| Что | Лимит | Ключ |
|---|---|---|
| весь API | 600 в минуту | IP |
| `POST /auth/session/login`, `POST /auth/register` | 20 в минуту | IP |
| запуск прогона, помощник, `POST /transcriptions`, загрузка файла | 60 в минуту | аккаунт |
| те же «дорогие» вызовы | 120 в минуту | IP (все аккаунты вместе: новые аккаунты лимит не обходят) |
| запросы с `Authorization: Bearer bps_…` | 600 в минуту | токен (отдельная таблица счётчиков, сверх лимита на IP; значения не формата `bps_…` не считаются); «дорогие» вызовы по токену идут в бюджет аккаунта владельца |

Окно скользящее, счётчики в памяти одного процесса и сбрасываются при перезапуске. Число ключей ограничено: при переполнении вытесняются самые давние.

## Устройство в коде

- `app/api/access.py` проверяет права на HTTP-уровне (`401`, `404`, `403`) и опирается на `AccessService` и `SharingService` (`app/services`).
- Запросы к БД лежат за портом `AccessRepository` (`infra/repositories/base.py`, SQL-реализация — `access_sql.py`). In-memory режим порт не реализует: аккаунты и ссылки требуют PostgreSQL.
- Слой `app.api` не импортирует `app.infra`; это проверяет import-linter.
- Подключение FastAPI Users — `app/services/auth.py`, маршруты и схемы — `app/api/auth.py`.
- Токены доступа: модель — `app/domain/api_tokens.py`, выпуск и проверка — `app/services/api_tokens.py`,
  маршруты — `app/api/v1/api_tokens.py`, хранение — `infra/repositories/api_tokens_sql.py`.

## Действия перед включением на существующей VM

1. Сделать резервную копию PostgreSQL и пользовательских файлов.
2. Сопоставить существующие приватные проекты с владельцами: выполнить backfill `projects.owner_id` для нужных строк. Миграция `0006` сбрасывает `public_read_only` у всех проектов, кроме демо из сида, и не назначает владельцев.
3. Проверить, что backend доступен по HTTPS, а `APP_ENV=production` задан в секретном окружении. Production требует HTTPS для входа; если HTTPS ещё нет, на стенде задайте `SESSION_COOKIE_SECURE=false` в серверном окружении.
4. Применить миграции и только затем включать `AUTH_ENABLED=true`.

Подтверждение email и восстановление пароля не настроены: для них нужен email-провайдер.

## Тесты

`make test-backend` не требует PostgreSQL. HTTP-тесты с включённой авторизацией (`tests/test_auth_http.py`:
гость, чужой проект, роли, ссылки, XML, миграция, отзыв доступа к уже открытым SSE и cookie WS-билета;
`tests/test_api_tokens_http.py` — токены доступа) запускает `make test-postgres` на временной схеме.

## Удаление и выход из общего проекта

Правила и ограничения: [ADR-0009](../adr/0009-project-deletion-and-leaving.md).

- `DELETE /projects/{id}`: owner удаляет проект для всех; editor/viewer удаляет только своё
  членство. Успех — 204. Удаление владельцем при активном прогоне — 409.
- `DELETE /projects/{id}/membership`: явный выход участника, 204; owner — 403.
- После выхода проект исчезает из `scope=shared`, данные остальных сохраняются. При действующей
  ссылке приглашение можно принять повторно. Общие демо-примеры не удаляются (403).
- После удаления owner, бывший участник и обладатель действовавшей ссылки получают 410 с
  `code=PROJECT_DELETED` и `detail=Автор удалил проект`. Для постороннего — 404. Квитанция
  действует 30 дней; затем 404. Данные проекта и файлы удаляются сразу.
- Для фронтенда: у общего проекта действие означает «Убрать из моих проектов»; у своего —
  «Удалить для всех». Машинный код 410 позволяет показать отдельное сообщение на открытой
  доске или по старой ссылке. Это API-контракт; новый интерфейс в этой ветке не добавляется.
