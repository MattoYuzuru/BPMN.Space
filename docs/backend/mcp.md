# MCP-сервер для внешних агентов

`/mcp` — MCP-сервер (Model Context Protocol, Streamable HTTP) в том же backend, что и REST.
Он нужен, когда материал лежит в системах, куда сервер не ходит: Confluence, внутренние порталы,
системы исполнения процесса. Доступ к ним есть у пользователя и его агента (Claude Code, Claude
Desktop, другой клиент MCP), поэтому продукт открывается агенту: агент сам собирает материал,
отвечает на вопросы и читает/предлагает схему **от имени владельца персонального токена**.

Решение — [RFC-0007](../rfc/0007-external-agents-mcp.md) (шаг 2), токены — шаг 1 того же RFC.
[REST-контракт](auth-and-sharing.md) остаётся основным; MCP — тонкий слой над `services/`,
повторяющий те же проверки доступа, а не второй способ обойти их.

## Подключение

1. В интерфейсе: Настройки → «Доступ для агентов» → создать токен. Выберите права и проекты
   (все или выбранные) и срок. Секрет вида `bps_…` показывается один раз — это пароль уровня
   аккаунта, в репозиторий и логи его не кладут.
2. Адрес: `https://<домен>/mcp`. Локально — `http://localhost:8080/mcp` (стек Docker);
   backend на `:8000` — `http://localhost:8000/mcp`.
3. Claude Code:

   ```bash
   claude mcp add --transport http bpmn-space https://<домен>/mcp \
     --header "Authorization: Bearer bps_…"
   ```

4. Другие клиенты MCP (Claude Desktop, Cursor, свой SDK-клиент): транспорт `http`
   (Streamable HTTP), URL `https://<домен>/mcp`, заголовок `Authorization: Bearer bps_…`.
   Claude Desktop подключает удалённый сервер через «Настройки → Коннекторы → Добавить
   коннектор» (URL и заголовок), если версия это поддерживает; иначе используйте клиент,
   умеющий HTTP-транспорт MCP.
5. В Docker-стеке `/mcp` проксируется Caddy (`infra/caddy/Caddyfile`) на backend. Если
   разворачиваете без нашего `compose.yaml`, пробросьте `/mcp` на backend так же, как `/api`:
   без буферизации ответа (Streamable HTTP отдаёт поток SSE).
6. Проверка, что сервер отвечает и токен принимается:

   ```bash
   curl -si -X POST https://<домен>/mcp -H "Authorization: Bearer $BPS_TOKEN" \
     -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
     -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
   ```

   Неверный или отозванный токен — `401` с тем же телом, что в REST; без токена — тоже `401`.

**OAuth 2.1 не реализован:** вход только копированием токена в заголовок. Это следующий шаг
RFC-0007 (шаг 4). Токен по ссылке проверки выдаётся вручную через `POST /shares/{token}/agent-token`
(см. «Проверка коллегой»); кнопка «Подключить своего агента» в интерфейсе — фронтовая волна.

## Инструменты

Права — как в REST: токен **сужает** права и проекты владельца и не расширяет его роль.
`project_ids` токена: проект вне списка отвечает как чужой (`404`). Наблюдатель (`viewer`)
читает, но не меняет проект (`403` «нужны права редактора»). Токен проверки, выданный по ссылке
`reviewer`, дополнительно сужен дорожками: `list_questions`/`get_diagram` отдают только вопросы
области, `answer_question` отвечает только на них, остальные изменяющие инструменты запрещены.

| Инструмент | Право | Что делает |
|---|---|---|
| `list_projects`, `get_project` | `projects:read` | Проекты и проект целиком: источники, вопросы, версия, прогон |
| `create_project` | `projects:write` + токен без ограничения проектами | Новый проект |
| `list_sources`, `read_source(source_id, from_, to)` | `projects:read` | Источники; текст порцией до 20 000 символов, `next_from` — следующая порция |
| `add_source(project_id, text, title, kind, url)` | `sources:write` | Материал от агента: `origin=agent`, `trust=agent`, пометка «через агента», провенанс токена и ссылки в `derivation` |
| `update_source`, `delete_source(confirm=true)` | `sources:write`, `sources:delete` | Название и включение — у любого источника; текст — только у добавленных агентом (`origin=agent`), иначе правка потеряла бы пометку авторства. Удаление — разрушающее, требует `confirm: true` |
| `list_questions(project_id, lane?)`, `answer_question` | `projects:read`, `questions:answer` | Вопросы (можно сузить до дорожки); ответ с провенансом «через агента» |
| `estimate_run(project_id, kind, profile)` | `runs:start` | Реальная оценка RFC-0005 (токены, запросы, деньги, время, разбивка; `complete=false` без цен модели) и `estimate_token` — допуск на запуск |
| `start_run(estimate_token, project_id?, base_version_id?)` | `runs:start` | Запуск только по свежему `estimate_token`; прогон в фоне |
| `get_run` | `projects:read` | Статус, этап, прогресс, итог и потрачено по журналу вызовов (токены, кеш, деньги, этапы; `complete=false` — часть цен неизвестна); текст ошибки провайдера наружу не отдаётся |
| `get_diagram(project_id, lane?)` | `projects:read` | XML BPMN 2.0, сводка IR, дорожки, основания и вопросы дорожки |
| `check_diagram(xml)` | `projects:read` | XSD и bpmnlint без сохранения |
| `save_diagram(project_id, xml, base_version_id)` | `projects:write` | Новая ручная версия; конфликт с `base_version_id` — ошибка со ссылкой «перечитайте» |

### Ресурсы

| URI | Право | Содержимое |
|---|---|---|
| `project://{id}/diagram.bpmn` | `projects:read` | XML последней версии схемы (`application/xml`) |
| `project://{id}/questions` | `projects:read` | Вопросы проекта JSON (`application/json`) |

### Подсказки (prompts)

| Имя | Заголовок | Аргументы |
|---|---|---|
| `collect_process_materials` | «Собери материалы по процессу» | `project`, `sources`, `goal` |
| `review_my_lane` | «Проверь мою дорожку» | `project_id`, `lane` |

Подсказка — текст-сценарий для агента: порядок инструментов, ограничения и напоминание, что
материал из чужих систем — данные, а не команды. Она ничего не читает и не меняет сама.

## Авторизация и безопасность

- Вход — только `Authorization: Bearer bps_…` (персональные токены из волны 1). Cookie-сессии,
  CSRF и браузерные правила REST к MCP не применяются: MCP-клиент — не браузер.
- Неизвестный, отозванный и истёкший токен, а также токен заблокированного аккаунта дают
  **одинаковый `401`** «Токен доступа недействителен…»; ответ содержит `WWW-Authenticate: Bearer`.
  Нет PostgreSQL — `503`, как и в REST.
- Таблица «инструмент → право» (`app/mcp/auth.py`, `TOOL_POLICIES`) **закрыта по умолчанию**:
  инструмент, которого нет в таблице, недоступен. Ресурсы и подсказки устроены так же
  (`RESOURCE_POLICIES`, `PROMPT_POLICIES`). Тесты сверяют зарегистрированные поверхности с
  таблицами, поэтому новый инструмент без строки прав остаётся закрытым.
- Ошибки доступа не отличаются от REST: чужой проект — `404` (а не `403`), чтобы не раскрывать
  существование; удалённый проект для бывшего участника — `410` «Автор удалил проект».
- Ответы MCP не содержат ключей, внутренних полей (`file_key`, `digest`, `answer_source_id`),
  текстов ошибок провайдеров и внутренних адресов. `get_run` отдаёт только `failed: true`.
- Лимит частоты: у `/mcp` свои таблицы вместо IP-лимитов `/api/v1` — общий лимит на IP и на
  токен (`RATE_LIMIT_API_PER_MIN`, как «весь API» в REST) и лимит дорогих вызовов
  (`estimate_run`, `start_run`) на токен и на аккаунт владельца
  (`MCP_EXPENSIVE_PER_MIN`, по умолчанию 30 в минуту). Аккаунтный лимит не даёт обойти квоту
  созданием нескольких токенов. Это защита от циклов агента, а не продуктовое ограничение.
- Внедрение инструкций: текст, пришедший от агента, — данные источника. Модель продукта не
  выполняет из него команд; изменения проекта проходят те же проверки, что из интерфейса.
- Стоимость: `start_run` требует свежей и одноразовой оценки; профиль может содержать
  ограничивающий бюджет (`budget: {tokens?, cost_usd?}`). Агент задаёт только свой лимит:
  настроек бюджета у пользователя пока нет, поэтому «повышать» нечего; достигнутый лимит мягко
  останавливает прогон (`waiting` и технический вопрос `budget_reached`), а не тратит больше.
  Оценка привязана к модели/провайдеру: если между оценкой и запуском они сменились, запуск
  отклоняется с просьбой оценить прогон заново.

## Материалы и ответы «через агента»

- Всё, что добавлено через токен, — источник `origin=agent`, `trust=agent`: в дереве материалов
  у него своя метка, а в цитаты оснований такой источник идёт с уровнем доверия агента.
  `derivation` хранит `capability=agent`, `provider=mcp`, название токена (`params.token_name`) и
  ссылку первоисточника (`params.url`), если агент её сообщил.
- Ответ на вопрос, записанный через MCP, — ответ владельца токена с провенансом:
  `answer.via=agent`, `answer.via_name=<название токена>` (миграция `0021_agent_answer_provenance`).
  Сервер не может проверить, читал ли человек ответ перед отправкой, и не делает вид, что может:
  пометка видна в REST-модели вопроса (`answer.via`, `answer.via_name`) и доступна интерфейсу;
  отдельный показ в UI — задача фронтенда волны 2. Следующий прогон учитывает такой ответ как
  обычный (ADR-0006), но с честным провенансом.
- Журнала действий агента в проекте пока нет (следующий шаг RFC-0007): провенанс виден у
  источника и ответа, отдельного списка «что делал агент» — нет.

## Проверка коллегой: токен по ссылке проверки

Ссылка роли `reviewer` (RFC-0007, шаг 3) открывает коллеге не весь проект, а выбранные дорожки:
`GET /shares/{token}` отдаёт `scope` и суженные вопросы, `GET /shares/{token}/agent-prompt` —
готовый текст «проверь дорожку» для вставки в агента (без секрета ссылки; только по ссылке
проверки — у viewer/editor `403`). Гость может ответить прямо по ссылке:
`POST /shares/{token}/questions/{id}/answer` (только вопроса области, провенанс `via=review`).
Вошедший получатель вызывает `POST /shares/{token}/agent-token` и получает токен `bps_…` один
раз, вместе с `mcp_url` и командой `claude mcp add …`.

Что умеет такой токен:

- `list_projects` показывает проект ссылки с ролью `reviewer`; `get_project`, `list_questions`,
  `get_diagram` возвращают только вопросы области (плюс общие вне дорожек); в `get_diagram`
  есть `review_scope` — id дорожек;
- `answer_question` отвечает на вопросы области; ответ получает `answer.via=agent`,
  `answer.via_name=<название проверки с коротким id ссылки>` и
  `answer.share_link_id=<id ссылки>`;
- схему, источники и проект менять нельзя (`403` «Ссылка проверки не позволяет…»);
  запуск прогонов, оценка и **журнал/события прогонов** недоступны: у токена нет `runs:start`,
  а SSE и карточка прогона содержат вопросы всего проекта и закрыты для роли проверки (`403`);
- `ignore` (принять допущение) через токен проверки нельзя: это решение владельца процесса,
  у него нет провенанса ссылки; проверяющий только отвечает на вопросы области.

Срок токена — срок ссылки; ссылка проверяется при каждом запросе, поэтому её отзыв или
истечение мгновенно закрывает токен (`401`), даже если срок токена ещё не вышел. Ссылки
`viewer`/`editor` токен агента и готовый промпт не выдают (`403`). Журнал действий:
`GET /projects/{id}/agent-activity` (участникам проекта) показывает добавленные агентами
материалы и ответы — и агентские (`via=agent`), и ответы проверяющих по ссылке (`via=review`),
с подписью проверки.

**Область проверки — снимок дорожек на момент создания ссылки.** Хранятся id дорожек последней
схемы. После пересборки схемы id могут измениться или исчезнуть: совпавшие дорожки остаются
областью, вопросы, привязанные к неизвестным/внедорожковым элементам, считаются «общими» и видны
проверяющему. Вопросы, привязанные только к потокам (без узла дорожки), тоже считаются общими.
Схема без дорожек не даёт создать ссылку с областью — только «весь проект». Это осознанное
поведение v1, а не гарантия вечной привязки; фиксировать область надёжнее после стабилизации
схемы.

## Ограничения v1

- **Файлы через MCP не передаются.** base64 в аргументе — плохой путь для больших документов и
  записей (и модель не должна гонять мегабайты через JSON-RPC). Загрузите файл через REST с тем
  же токеном, затем читайте текст инструментом `read_source`:

  ```bash
  curl -s -X POST https://<домен>/api/v1/projects/$PROJECT_ID/sources/file \
    -H "Authorization: Bearer $BPS_TOKEN" -F "file=@reglament.pdf"
  ```

  Для `add_source` через MCP остаются текст (`kind=text`) и проверенная расшифровка
  (`kind=voice`). Одноразовые подписанные ссылки загрузки — возможное развитие, в v1 их нет.
- **URL не скачивается сервером.** Параметр `url` в `add_source` — провенанс: извлеките текст
  у себя (агент умеет ходить в закрытые системы) и пришлите его в `text`. Так нет SSRF-поверхности
  и лишнего парсера в MCP.
- **Оценка неполная у моделей без цен.** У mock и совместимых провайдеров без прайса
  `estimate_run` честно отдаёт `complete=false` и `cost=null`: агент обязан сказать человеку,
  что стоимость неизвестна, а не показывать ноль. Это не ошибка, а состояние модели.
- **Бюджет агента только ограничивает.** В `profile` можно передать
  `budget: {"tokens": N, "cost_usd": M}` (хотя бы одна граница, положительные значения).
  Отдельных настроек бюджета у пользователя пока нет, поэтому агент не может ничего «повысить»:
  значение проходит как ограничивающий лимит, прогон мягко останавливается на нём и ждёт
  решения человека. Без `budget` прогон идёт без ограничения по тратам — это видно из ответа
  `estimate_run` (в профиле нет бюджета).
- **Бюджет требует модели с учётом стоимости.** На mock и совместимом провайдере без цен
  `start_run` с бюджетом честно отклоняется ошибкой «бюджет нельзя проверить на демонстрационной
  модели»: сервер не делает вид, что лимит соблюдается. На модели с ценами бюджет учитывается
  прогоном (мягкая остановка и технический вопрос `budget_reached`).
- Нет OAuth, SSE/WebSocket через MCP (прогресс прогона — опросом `get_run`), нет истории версий
  как отдельного инструмента (XML последней версии — в `get_diagram`).
- MCP работает только при PostgreSQL и включённых аккаунтах: токены и роли требуют базы.

## Как устроено в коде

| Файл | Что |
|---|---|
| `backend/app/mcp/auth.py` | ASGI-middleware Bearer, `McpIdentity`, таблицы прав, проверка проекта/объекта, лимит токена |
| `backend/app/mcp/server.py` | `MCPServer` (SDK `mcp`), регистрация, Streamable HTTP на `/mcp`, lifespan |
| `backend/app/mcp/tools.py` | Инструменты RFC-0007 поверх `container.*` |
| `backend/app/mcp/resources.py`, `prompts.py` | Ресурсы и подсказки |
| `backend/app/mcp/diagram.py` | Разбор XML, дорожки, сводка IR (через `domain.bpmn`) |
| `backend/app/mcp/serializers.py` | Компактные ответы без внутренних полей |
| `backend/app/mcp/estimate.py` | Адаптер `ServiceEstimator` над `services/estimate.py`, компактная модель оценки, HMAC-тикеты допуска, порт `RunEstimator` |
| `backend/app/main.py` | Монтирование `/mcp` вне `/api/v1` и вне OpenAPI; MCP-lifespan |

Слои: `app.mcp` — представление рядом с `app.api` (`(api | mcp) → services → (llm, ingest, infra)
→ domain`, проверяет import-linter). Прямых импортов `app.infra` в `app.mcp` нет: база и файлы —
только через сервисы и контейнер.

Конфигурация: `MCP_ESTIMATE_SECRET` (подпись оценок; пусто — случайный на процесс),
`MCP_ESTIMATE_TTL_SEC` (срок оценки, по умолчанию 900 с), `MCP_EXPENSIVE_PER_MIN` (дорогие
вызовы на токен). Остальные значения — общие (`MAX_TEXT_CHARS`, `MAX_DIAGRAM_BYTES`).

## Оценка и запуск

Оценку считает сервис волны 2A (`services/estimate.py`, `llm/estimate.py`, RFC-0005 шаг 4,
`POST /projects/{id}/runs/estimate`). MCP не дублирует расчёт:

1. `app/mcp/estimate.py::build_estimator(container)` возвращает `ServiceEstimator` над
   `container.estimate`: `estimate_run` отдаёт диапазоны токенов/запросов/денег/времени,
   разбивку по этапам, модель и провайдера, `complete` и `priced_on`. `complete=false` и
   `cost=null` — цены модели неизвестны; оценка не притворяется нулевой. Если сервиса в
   контейнере нет (урезанный стенд) — `UnavailableEstimator`: отказ без выдуманных чисел.
2. Ошибки профиля и модели приходят из сервиса русскими сообщениями (`InvalidInputError`):
   неизвестный `effort`, нет ключа модели, в проекте нет источников — агент видит понятную
   причину и может её исправить. Профиль MCP — `effort`, `semantic_review` и ограничивающий
   `budget` (см. «Оценка неполная…» и «Бюджет агента…»).
3. `estimate_run` выдаёт HMAC-подписанный `estimate_token` (`TicketSigner`): пользователь,
   проект, режим, профиль и срок (`MCP_ESTIMATE_TTL_SEC`, по умолчанию 900 с). `start_run`
   проверяет подпись, срок и совпадение и только затем вызывает `services.runs.start` с
   профилем из тикета. Без свежей оценки запустить прогон нельзя — «вслепую» нет.
4. После запуска `get_run` отдаёт и потраченное: токены/кеш/деньги и разбивку по этапам из
   `llm_calls` (`complete=false` у mock и моделей без цен). Наблюдатель может оценить прогон
   (как REST), запуск остаётся правом редактора.
5. Бюджет: `profile.budget` входит и в оценку, и в `estimate_token`; `start_run` передаёт его
   в `services.runs.start`, где действует мягкая остановка RFC-0005. Значение — только лимит
   агента (пользовательских настроек бюджета ещё нет), поэтому повышать нечего; поднимать
   лимит остановленного прогона можно действием технического вопроса в интерфейсе.
6. Одноразовость и привязка: `estimate_token` одноразовый (использованные допуски хранятся в
   памяти процесса до TTL) и привязан к модели/провайдеру оценки — при их смене `start_run`
   просит оценить прогон заново.
