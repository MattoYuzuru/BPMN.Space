# Записи и производные источники

Как сервер обрабатывает аудио, видео и сканы PDF и как устроено дерево материалов. Исходное
решение по записям — [ADR-0012](../adr/0012-long-documents-and-media.md) п. 4 (пределы, ffmpeg,
сегменты, повторы); дерево материалов — шаг 3, OCR и видео — шаги 4–5
[RFC-0006](../rfc/0006-tools-connectors-and-derived-sources.md). Этот документ описывает текущее
поведение; ADR остаётся записью решения.

## Что создаёт загрузка записи

`POST /projects/{id}/sources/file` с `.mp3 .wav .ogg .opus .m4a .flac .aac .webm .mp4 .mov .mkv`
пишет файл на диск потоком (`MAX_MEDIA_BYTES`), принимает необязательное поле `media_profile`
(`audio` — только звук, `sparse` — звук и редкие кадры, `detailed` — подробно; по умолчанию
`audio`) и в одной транзакции создаёт два источника:

| Узел | Поля | Текст |
|---|---|---|
| Исходный файл | `kind=file`, `origin=user`, `trust=primary`, `file_name`, `size_bytes`; после обработки `duration_sec` и `media` (`has_audio`, `has_video`) | нет: в модель не идёт |
| «Расшифровка: <название>» | `kind=text`, `origin=derived`, `trust=extracted`, `parent_id` записи, `derivation` | строки `[мм:сс] реплика` |

`derivation` расшифровки: `capability=speech_to_text`, фактический `provider` и `model`
(кто ответил: Deepgram `nova-3`, OpenAI/Groq Whisper, совместимый сервер или серверный `mock`),
`params` (`segment_sec`, `block_sec`, формат звука, был ли ffmpeg; после обработки — `duration_sec`,
`minutes` и `language`), `cost_usd` (`null`, пока провайдер стоимость не сообщает; поле готово для
оценки), `credential_id` (ключ пользователя, которым оплачен вызов; `null` — серверный
провайдер: по нему потом считается расход по плательщику), `created_at`.

API возвращает исходный файл; оба узла видны в `GET /projects/{id}` плоским списком, дерево
строится по `parent_id`. Счётчик источников проекта считает только исходные материалы.

Видео с профилем `sparse`/`detailed` после расшифровки получает ещё производные узлы — кадры,
описание экрана, общую ленту и краткое содержание (см. ниже). Профиль `audio` сохраняет прежнее
поведение: только запись и расшифровка.

## Распознавание на ключах пользователя

Запись расшифровывается на ключах **инициатора загрузки** (RFC-0006): `create_media` выполняется
в запросе пользователя, а фоновая задача `process_file` получает его `initiator_id`. Ключи типа
`speech_to_text` перебираются по приоритету маршрутизатором (`services/capability_router.py`):
в каталоге `ingest/adapters/` живут Deepgram и OpenAI-совместимый адаптеры (OpenAI, Groq, любой
сервер с `/audio/transcriptions`). Серверный `STT_PROVIDER`/`DEEPGRAM_API_KEY` остаётся
**запасным путём** — для production без ключей пользователя, для гостя по ссылке доступа и после
того, как ключи пользователя не сработали. `STT_PROVIDER=none` отключает запасной путь: стенд
только на ключах пользователей, а запись без ключа завершается понятной ошибкой «добавьте ключ»,
а не заготовленным текстом (`mock` production не принимает). Ключи инициатора передаются аргументом, а не хранятся
в источнике: после рестарта `processing`-источники всё равно завершаются сбоем (ADR-0012), так что
переживать рестарт ключам не нужно. Голосовая заметка `POST /transcriptions` использует ключи
**вызывающего** пользователя.

Отказ маршрутизации — это не безликое «не удалось»: источник и расшифровка становятся `failed` с
понятным русским текстом, `warning` записи сообщает, что уже обработано и что осталось, а
`derivation.params.routing` хранит структурный результат
`{status, reason, capability, done, remaining, alternatives}` без текста провайдера. Классы
причин — `quota_exhausted`, `auth`, `transient`, `unsupported`, `fatal`; при исчерпанной квоте
ключ получает `exhausted_until`, при отказе ключ выключается и пользователь видит ошибку в
настройках. Это же событие через `TechnicalQuestionIncidentSink` превращается в неблокирующий технический
вопрос проекта (`services/technical_questions.py`): «у ключа закончилась квота», «ключ отклонён»,
«возможность не подключена»; у вопроса есть действия «Открыть настройки», «Повторить»,
«Продолжить без этого». Временный сбой и фатальная ошибка вопроса не создают. У
`POST /transcriptions` структурный отказ — `503` с полями `code`, `done`, `remaining`,
`alternatives`.

## Профили обработки и оценка стоимости

Профиль выбирается при загрузке и влияет только на видеоряд; звук расшифровывается всегда, если
он есть. Порог смены сцены и шаг периодического кадра заданы профилем в `ingest/frames.py`:

| Профиль | Смена сцены | Кадр не реже | Предел кадров | Что появится в дереве |
|---|---|---|---|---|
| `audio` (по умолчанию) | — | — | — | запись и «Расшифровка» |
| `sparse` | `scene > 0.35` | 90 с | 120 | + «Ключевые кадры», «Описание экрана», «Общая лента», «Краткое содержание» |
| `detailed` | `scene > 0.20` | 20 с | 600 | то же, кадров больше |

До загрузки фронтенд запрашивает `POST /projects/{id}/sources/media/estimate` с
`{duration_sec, has_video, media_profile}`: в ответе минуты распознавания речи, нижняя и верхняя
границы числа кадров, число запросов к vision-модели и ориентировочная цена (`total_cost_usd`,
диапазон `min_usd`…`max_usd`, дата проверки цен `priced_on`). Цена считается по каталогу:
распознавание — по минутным ценам провайдеров, vision — по ценам изображений моделей Claude из
справочника `llm/capabilities.py` и ориентировочным публичным ценам OpenAI, краткое
содержание — отдельной строкой `summary_cost_usd` (один запрос по началу записи; для профиля
«только звук» его нет). Верхняя граница кадров дополнительно ограничена серверной настройкой
`MEDIA_FRAME_MAX_FRAMES`. Это оценка «от и до», а не обещание: фактическая стоимость попадает в
`derivation.cost_usd` производного узла.

## Кадры видео

`ingest/frames.py` делает два прохода ffmpeg: кадры смены сцены (`select='gt(scene,T)'`) и
периодические кадры (`fps=1/N`). Если оба прохода не дали ни одного кадра (короткая запись,
статичный экран), берётся первый кадр записи — иначе описывать было бы нечего. Кадры
уменьшаются до `MEDIA_FRAME_WIDTH` (768 px) и сохраняются JPEG.

Почти одинаковые кадры отбрасываются перцептивным dhash: ffmpeg отдаёт кадры как rawvideo
gray 16×16, приложение сравнивает соседние пиксели строк (240 бит) и считает расстояние
Хэмминга; кадры с расстоянием не больше `MEDIA_FRAME_DEDUP_BITS` бит считаются дублями. Хеш
сопоставляется кадру по пути файла, а не по порядку в списке: кандидаты приходят из двух
проходов и сортируются по времени, поэтому позиционное сопоставление сравнивало бы чужие
кадры. Кадры одного момента (сцена и периодический кадр совпали) не дублируются. Pillow не
используется: на VPS остаются только ffmpeg/ffprobe (RFC-0006).

Кадры лежат в том же uploads-хранилище, что и записи (ключи — в
`derivation.params.frames` узла «Ключевые кадры»), удаляются вместе с записью и её производными.
Число кадров ограничено профилем и `MEDIA_FRAME_MAX_FRAMES`; ширина —
`MEDIA_FRAME_WIDTH`; таймаут извлечения — `MEDIA_FRAME_FFMPEG_TIMEOUT_SEC`. Одновременных
извлечений на процесс — `MEDIA_FRAME_MAX_CONCURRENT` (по умолчанию 1): каждая запись запускает
2–3 процесса ffmpeg, и без семафора несколько загрузок забирают CPU у остальных задач. Состояние
прохода (stderr, время кадров) живёт только внутри одного вызова: экстрактор общий, и общий
атрибут смешал бы время кадров параллельных записей. Временная папка удаляется всегда, даже при
ошибке; кадры, которые так и не стали частью дерева (сбой до создания узла), удаляются из
хранилища. Если кадры не извлеклись, запись и расшифровка остаются готовыми, а в предупреждении
источника появляется причина: звук — главный материал, кадры — дополнение.

## Производные узлы видео

После успешной расшифровки и только для видео с профилем `sparse`/`detailed` сервер создаёт:

| Узел | `trust` | Что внутри | `derivation` |
|---|---|---|---|
| «Ключевые кадры (N): <название>» | `observed` | строки `[мм:сс] кадр N`, ключи файлов кадров | `capability=frames`, `provider=ffmpeg`, `cost_usd=0` |
| «Описание экрана: <название>» | `observed` | строки `[мм:сс] описание экрана` и видимый текст | `capability=vision`, фактическая модель, `cost_usd` |
| «Общая лента: <название>» | `observed` | события `[мм:сс] речь: …` / `экран: …` по времени, сводится кодом | `capability=media_feed`, `provider=code`, `cost_usd=0` |
| «Краткое содержание: <название>» | `summary` | 5–10 пунктов для навигации | `capability=summary`, модель, `cost_usd` |

Описание экрана строится пачками (`MEDIA_VISION_BATCH_SIZE` кадров в запросе) с ограниченной
параллельностью; сбой одной пачки не отменяет остальные. Если часть кадров не описана, узел
`ready` с тем, что получилось, а у записи — предупреждение. Краткое содержание не идёт в
контекст модели и не может быть основанием цитаты (`trust=summary`): это навигация, а основание —
расшифровка (`extracted`) и описание экрана (`observed`).

Модель для vision выбирает `ModelResolver.resolve_media`: ключ модели пользователя-инициатора
загрузки с `vision`/`pdf_input`, затем модель сервера, в демо — `mock`. Если подходящей модели
нет, производные кадры создаются (это работа кода), а описание экрана пропускается с
неблокирующим техническим вопросом `capability_missing` — отказ виден пользователю, но материал
не теряется. Пока идёт описание, узел «Описание экрана» уже `processing`: контекст прогона
видит, что видеоряд ещё обрабатывается, и не считает материалы полными раньше времени.

**Что идёт в контекст модели.** Расшифровка (`extracted`) и описание экрана (`observed`) —
основания: модель видит их и может цитировать с таймкодом. «Ключевые кадры» и «Общая лента»
остаются в дереве для навигации и в контекст не идут: первое — список таймкодов без
содержания, второе дублирует расшифровку и описание экрана. «Краткое содержание» —
`trust=summary`, тоже только навигация. Эти исключения заданы в `Source.feeds_model`
(`domain/media.py`, `NAVIGATION_CAPABILITIES`).

## OCR сканов PDF

Если разбор PDF оставил `unreadable_pages` (страницы без текстового слоя, ADR-0012), фоновая
обработка запускает OCR. Чистый скан, в котором текстового слоя нет ни на одной странице, —
самый частый случай: разбор помечает источник `failed`, но сохраняет номера страниц, OCR
запускается автоматически, и после успеха источник становится `ready` (при частичном
распознавании — `ready` с предупреждением и остатком `unreadable_pages`). Если модели нет,
источник остаётся `failed` с техническим вопросом; `POST /sources/{id}/ocr` восстановит его
после настройки ключа (409 — только когда распознавать действительно нечего). Модель с чтением PDF (Anthropic `document` block) получает сам PDF или
его части. На один блок — до 32 МБ **закодированного** запроса и 600 страниц, поэтому крупный
скан режется на части по 22 МиБ сырых байт (base64 добавляет около трети) и по
`OCR_PAGES_PER_REQUEST` страниц; если после нарезки часть всё равно больше лимита, она делится
пополам. Части собираются из исходных страниц без перерисовки (pypdf), но модель видит
фрагмент из 1..N страниц, поэтому её просят вернуть **порядковые** номера внутри фрагмента, а
сервер переводит их обратно в исходные. Ответ — JSON `{"pages": {"1": "…"}}`; допускается
разметка `[Страница N]` с порядковыми номерами. Разобранный, но непригодный JSON не
подменяется сырым ответом: лучше не распознать страницу, чем записать в неё JSON. Неразмеченный
сырой текст принимается только для фрагмента из одной страницы.

Потолок ответа считается от числа страниц части (`OCR_TOKENS_PER_PAGE`, не больше
`OCR_MAX_TOKENS` и максимума модели): фиксированные 4 тыс. на десять плотных страниц обрезали
ответ. Если провайдер всё же обрезал ответ (`OutputTruncatedError`), часть делится пополам и
распознаётся повторно — страницы не теряются, а вход уже оплачен. PDF нарезается в отдельном
потоке: pypdf не блокирует event loop, и `PdfSource` читает документ один раз, а не заново на
каждую часть.

Результат — производный узел «OCR: <название>» (`origin=derived`, `trust=extracted`,
`capability=ocr`, фактический провайдер/модель, `cost_usd`, `params.pages`). Родительский
источник остаётся `ready`, его `unreadable_pages` сокращается до нераспознанных страниц, а
`warning` обновляется или снимается. Если модели нет — источник не меняется, появляется
неблокирующий технический вопрос `capability_missing`. Если часть страниц не распознана, узел
`ready` с распознанным, а остаток остаётся в `unreadable_pages` с предупреждением.

`POST /sources/{id}/ocr` (токену нужны `sources:write` и `runs:start` — это платная работа)
повторяет OCR после настройки ключа: узел перезапускается в `processing`, готовые страницы не
распознаются заново — текст и `cost_usd` накапливаются. Если повтор не удался (ключ, квота,
обрезанный ответ), узел с уже распознанным текстом остаётся `ready`, а нераспознанные страницы
остаются в `unreadable_pages` c предупреждением, поэтому ранее оплаченный текст не исчезает из
контекста. Два одновременных `POST /ocr` не создают два узла: пока узел `processing`, второй
запрос получает его же. Без подходящей модели — `503` с `code=capability_missing` и действиями
технического вопроса. Внешние OCR-провайдеры (Mistral OCR, Yandex Vision OCR) зарегистрированы
в реестре `AdapterSpec` как контракты: ключ сохраняется, вызовы включит следующая волна; OCR в
этой волне выполняет модель.

## Плеер и таймкоды

`GET /sources/{id}/media` отдаёт аудио или видео записи из uploads с поддержкой HTTP Range:

- `200` — весь файл; `Accept-Ranges: bytes`, `ETag`, `Last-Modified`, `Content-Type` по MIME;
- `HEAD` — те же метаданные и права без тела (проверка доступности и кэша);
- `206` — запрошенный диапазон (`Range: bytes=a-b`, `bytes=a-`, `bytes=-n`) с `Content-Range`;
- `416` — диапазон вне файла или несколько диапазонов сразу (плееру достаточно одного);
- `304` — по `If-None-Match`/`If-Modified-Since`;
- доступ — владельцу и участникам проекта (viewer читает), токену нужно право `projects:read`;
  посторонним — `404`, как и остальные чужие объекты. Документы этим маршрутом не отдаются.

`GET /sources/{id}/segments` отдаёт отрезки расшифровки (`start_sec`, `end_sec`, `text`,
`speaker`), чтобы плеер перематывал к цитате `[мм:сс]` без разбора текста на клиенте. Работает и
для записи (берётся её расшифровка), и для самой расшифровки.

## Статусы и сбои

Оба узла сразу `processing`. Фоновая обработка (`SourceService.process_file` →
`_process_media`): `ffprobe` (длительность, звук, видео; обложка mp3 видео не считается) →
ffmpeg режет звук на сегменты → маршрутизированный STT с ограниченной параллельностью (временный
сбой ключа повторяет маршрутизатор, сегмент — ещё один внешний повтор) → склейка `[мм:сс]`. Итог записывается точечным `patch` обоих узлов под блокировкой проекта и только
пока они в `processing`:

- успех — запись `ready` с длительностью и дорожками, расшифровка `ready` с текстом;
- сбой (нет звуковой дорожки, сегмент не расшифрован после повтора, кончились рабочие ключи
  распознавания, нет речи, превышен `MAX_TEXT_CHARS`, ffmpeg недоступен) — **оба** `failed` с
  одной причиной; дорожки записи сохраняются, если ffprobe успел их прочитать; при отказе
  маршрутизации к причине добавляются покрытый и оставшийся диапазоны, а `warning` записи и
  `derivation.params.routing` хранят структурный результат;
- рестарт сервера во время обработки — оба `failed` (как документы, ADR-0012);
- расшифровки к началу обработки нет — STT не вызывается, запись `failed` с причиной «Расшифровка записи удалена до окончания обработки».

Аналитик может вписать текст в неудавшуюся расшифровку: она становится `ready` с
`edited_by_human=true`, а запись выходит из `failed`. Без ffmpeg работает только mock-STT
на небольшом файле (одним блоком `[00:00]`); дорожки тогда неизвестны (`media` с `null`).

Голосовые заметки с микрофона (`POST /transcriptions` → `POST /sources/text`, `kind=voice`)
не меняются: это один источник `origin=user`, текст проверил аналитик.

## Правка, выключение, удаление

- `PATCH /sources/{id}` с новым текстом производного источника ставит `edited_by_human=true`
  (тот же текст — не правка). Ревизий нет: правка перезаписывает текст ИИ, а цитаты на
  изменённые места перестают находиться так же, как у любого правленого источника.
  Ревизии и пересвязывание цитат — задача #34 (RFC-0006, шаг 7).
- У записи своего текста нет: правка `content` записи — `422`. Название править можно.
- Выключение записи (`active=false`) выключает её производные, включение — включает.
  Производный узел можно выключить отдельно.
- Удаление записи удаляет производные: в PostgreSQL — составной FK с `ON DELETE CASCADE`,
  в in-memory режиме — так же явно; файлы удаляются после фиксации. Удаление проекта удаляет
  файлы источников и файлы кадров производных узлов (кадры хранятся отдельными ключами в
  `derivation.params.frames`, а не в `file_key`). Удаление расшифровки
  оставляет запись, но пока расшифровка `processing`, удалить её нельзя (`409`): распознавание
  уже идёт и оплачивается — удаляется запись целиком или после окончания. ffprobe, ffmpeg и STT
  одной записи идут одной задачей под общим семафором `MEDIA_MAX_CONCURRENT_JOBS`.
- Создать источник с `parent_id` вручную нельзя: `POST /sources/text` отклоняет лишние поля
  (`422`), производные создаёт только сервер, а сервис проверяет, что родитель — источник
  того же проекта.

## Контекст прогона

Модель читает расшифровку, а не запись: правила отбора и уровни доверия —
[generation-quality.md](generation-quality.md#какие-источники-видит-модель-и-уровни-доверия-rfc-0006).
Хеш снимка источников совместим с прогонами, запущенными до миграции 0016
([persistence.md](persistence.md)).

## Не сделано

Кеш производных по хешу `(parent, capability, provider, model, params)` (повтор после
технического вопроса может снова оплатить запрос модели), `video_understanding` (видео целиком
вместо кадров), автоматический срок хранения кадров (кадры удаляются вместе с записью, но TTL
ещё не чистит старые файлы), вызовы внешних OCR-провайдеров Mistral/Yandex (только контракты),
веб-поиск и чтение страниц, синтез речи, ревизии производных (#34). Старые записи, загруженные
до 0016, остаются одним источником с текстом; записи, загруженные до волны 3, не получают
профиль обработки и остаются «только звук».
