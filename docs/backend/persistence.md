# PostgreSQL и миграции

Локальный Compose поднимает PostgreSQL 16 и автоматически применяет Alembic-миграции при старте
backend. Данные БД лежат в Docker volume `postgres_data`, загруженные документы и аудио — в
`uploads_data` (`/data/uploads`). Обычные `docker compose down` и пересборка контейнеров эти данные
не удаляют. `docker compose down -v` удаляет оба volume вместе с данными.

## Что сохраняем

- `projects` — название, описание и даты изменения.
- `sources` — текст, тип и статус источника, метаданные загрузки, ключ файла в volume и место
  для кэшированного дайджеста. Дерево материалов (миграция `0016_source_derivation`,
  [RFC-0006](../rfc/0006-tools-connectors-and-derived-sources.md)): `origin`
  (`user`/`derived`/`agent`/`answer`), `parent_id`, `derivation` (JSONB: возможность, провайдер,
  модель, параметры, стоимость, время), `trust`, `edited_by_human`, `media` (JSONB: есть ли звук
  и видео у записи). Родитель — источник **того же проекта**: составной внешний ключ
  `(parent_id, project_id) → sources(id, project_id)` с `ON DELETE CASCADE` (удаление записи
  удаляет её расшифровку) и `CHECK parent_id <> id`. Миграция заполнила старые строки:
  ответы — `origin=answer`, прочие — `origin=user`, все — `trust=primary`; старые записи с
  расшифровкой в самом источнике остаются одним узлом. Откат 0016 не теряет данных: текст, статус и ошибка расшифровки возвращаются в запись, цитаты вопросов (`about`/`evidence`) и версий (`trace`) переводятся на запись, затем строки расшифровок удаляются; другие производные узлы (не `speech_to_text`, вложенные, несколько на запись, запись со своим текстом) — явный отказ отката. FK и CHECK создаются `NOT VALID` и затем `VALIDATE`.
  Устройство записей и производных — [media-and-derived-sources.md](media-and-derived-sources.md).
  Миграция `0024_agent_search` добавляет GIN-индекс
  `to_tsvector('russian', title || ' ' || content)` для инструмента `search_sources` агентного
  режима (RFC-0004). Запрос репозитория повторяет выражение индекса буквально, иначе
  планировщик не сопоставит условие с индексом. Без индекса поиск работает, но читает таблицу
  целиком; откат удаляет только индекс, данные не теряются.
- `questions` — статус, важность, текст, цитаты-доказательства, ответ и элементы BPMN. Один
  answer-источник может быть связан только с одним вопросом. Провенанс ответа: `answer_via`
  (`agent` — ответ записал внешний агент через MCP), `answer_via_name` (название токена) и
  `answer_share_link_id` (ответ по ссылке проверки, миграция `0023_reviewer_role`, FK с индексом);
  миграция `0021_agent_answer_provenance`, [RFC-0007](../rfc/0007-external-agents-mcp.md).
  Миграция `0019_technical_questions` (RFC-0006, шаг 2) добавляет категорию (`business` по
  умолчанию, `technical` для вопросов о материалах и запуске с ограничением значений), действия
  технического вопроса (`actions`, JSONB) и блокирующий флаг `blocking`. Технические вопросы не
  попадают в контекст модели и IR; их создаёт `services/technical_questions.py`.
- `runs` — режим, статус/этап/прогресс, сводка вопросов, снимки анализа и структуры, отчёт,
  модель, время выполнения, ошибка, предупреждения (`warnings`: например, контекст модели был
  обрезан) и ссылка на созданную версию. Статус `waiting` (RFC-0005, шаг 5; RFC-0006, шаг 2)
  означает ожидание действия по блокирующему техническому вопросу: прогон остаётся активным,
  `ir.execution.profile` хранит бюджет, по которому он остановлен, а `POST /runs/{id}/resume`
  продолжает работу. Агентный режим (RFC-0004) хранит там же `mode`/`max_steps` профиля и
  `ir.execution.agent`: число оплаченных ходов, журнал вызовов инструментов (имена и
  SHA-256 аргументов/результатов, без текстов источников) и принятый `submit` — вопросы и
  канонический IR. Это позволяет восстановлению (ADR-0008) перепроверить сданный результат и
  не оплачивать прогон повторно, а незавершённый цикл продолжить с тем же счётчиком ходов.
- `diagram_versions` — BPMN XML, происхождение, номер, diff, отчёт проверки, цитаты и дорожки;
  сессия правок (`session_started_at`, `updated_at`, `saved_count`), контрольная точка
  (`checkpoint`, `label`), счётчики проверки и флаги общих метаданных (см. ниже).
  Один прогон может создать не более одной версии; ссылки прогона и версии проверяются внешними
  ключами.
- `llm_calls` — запрос и результат каждого этапа пайплайна, этап, задержка и токены
  (`tokens_in`/`tokens_out` — сумма по всем запросам этапа из поля `usage` провайдера; у mock
  остаются `null`). С миграцией `0018_llm_call_cost` (RFC-0005, шаг 4) здесь же раздельный
  учёт кеша (`cache_read_tokens`/`cache_write_tokens`), стоимость `cost_usd` по ценам
  справочника на момент вызова, дата цен `price_checked_on` и `model` (у неизвестной цены —
  `null`, total помечается неполным). Репозиторий отдаёт `list_by_run` и `totals` (агрегат по
  этапам одним запросом; вызов, прерванный до запроса к провайдеру, помечается нейтральным
  и не делает итог неполным навсегда). Запрос хранится в компактном виде: вместо текстов источников и XML —
  их `id`, длина и SHA-256 (`ingest/context.py:describe_context`). Так таблица не раздувается
  копиями документов на каждый вызов, а по хешу видно, какая версия текста была у модели; сами
  тексты лежат в `sources`. В агентном режиме (RFC-0004) один ряд `stage=agent` — один ход
  модели: вместо текстов там имена вызванных инструментов и SHA-256 аргументов и результатов,
  поэтому журнал воспроизводим и не раскрывает материалы.

- `user_onboarding` и `user_onboarding_items` (миграция `0008_onboarding`) — состояние тура
  (статус, шаг, учебный проект), скрыт ли чек-лист «Начало работы» и отмеченные пункты чек-листа
  (`PRIMARY KEY (user_id, item_key)`, отметка `INSERT … ON CONFLICT DO NOTHING`: повтор не меняет
  `completed_at`). Строка `user_onboarding` создаётся лениво при первом обращении; удаление
  пользователя убирает обе таблицы (`CASCADE`), удаление учебного проекта обнуляет
  `tour_project_id` (`SET NULL`). Устройство — [onboarding.md](onboarding.md).
- `user_credentials` (миграция `0020_user_credentials`, раньше `user_llm_credentials` из
  `0014_user_llm_credentials`) — ключи пользователя по типам задач (RFC-0006): `kinds`
  (`varchar[]`: `llm`, `speech_to_text`, `ocr`, `vision`, `video`, `web_search`, `web_fetch`,
  `tts`; CHECK на непустоту и известные значения), провайдер, название, адрес (только у
  совместимого), **шифртекст** ключа (Fernet), подсказка из последних 4 символов, модель по
  умолчанию, `priority` (0…1000, меньше — раньше), `enabled`, `monthly_limit` (JSONB: минуты,
  запросы, деньги), `exhausted_until` и `last_error_code` (класс отказа маршрутизации),
  `last_used_at`, `last_error`, `is_default` (частичный уникальный индекс: не больше одного
  ключа модели на пользователя). Удаление пользователя убирает ключи (`CASCADE`). Открытого
  ключа в БД нет. Миграция переносит старые ключи моделей без потери данных (`kinds={llm}`,
  приоритет 100, включены, отметки использования и ошибки сохраняются). Старая таблица
  `user_llm_credentials` **намеренно остаётся legacy-копией** до следующего релиза: откат только
  кода (scripts/deploy.sh переключает релиз, не схему) должен запускать старый код. Откат
  `downgrade` переносит ключи `llm`, созданные после релиза, обратно в `user_llm_credentials`,
  удаляет `user_credentials`; ключи инструментов (не-LLM) при откате теряются — см.
  [deployment.md](../deployment.md#откат-через-волну-2-обобщённые-ключи-технические-вопросы-mcp).
  Устройство —
  [подключение-провайдеров.md](подключение-провайдеров.md), решения —
  [ADR-0011](../adr/0011-user-llm-credentials.md), [RFC-0006](../rfc/0006-tools-connectors-and-derived-sources.md).
- `api_tokens` (миграции `0017_api_tokens`, `0023_reviewer_role`) — персональные токены доступа
  для внешних агентов; токен по ссылке проверки дополнительно хранит `share_link_id` (FK с
  индексом, `ON DELETE CASCADE` — токен умирает вместе со ссылкой и не превращается в обычный)
  и `lane_ids` (область дорожек), проверяется по живой ссылке при каждом запросе. Откат
  `0023` гасит reviewer-ссылки (`revoked_at`), а не понижает их до viewer на весь проект.
  (RFC-0007): владелец (`CASCADE` при удалении пользователя), название, префикс `bps_…` для
  опознания, **SHA-256** секрета (уникальный индекс; открытого секрета в БД нет), права
  (`varchar[]`, проверка допустимых значений и непустоты), `project_ids` (`uuid[]`, `NULL` — все
  проекты пользователя), обязательный `expires_at` (больше `created_at`), `last_used_at` (не чаще
  раза в минуту, условием в самом `UPDATE`) и `revoked_at`: отзыв — отметка, строка остаётся для
  истории. Правила — [auth-and-sharing.md](auth-and-sharing.md#токены-доступа-для-агентов).
  `0017` откатывается `alembic downgrade 0016_source_derivation`.
- `runs.created_by` — кто запустил прогон (`SET NULL` при удалении пользователя): прогон
  завершается в фоне, и по этому полю чек-лист отмечает `diagram_built` и `diagram_rebuilt`
  тому, кто запустил, а не владельцу проекта. `0008` откатывается `alembic downgrade -1`.

Сгенерированные прогоны сохраняют нормализованный GraphIR v1 в `runs.ir`, анализ и результат
проверки — в отдельных JSON-полях. XML строит компилятор; ручная семантика и её защищённые
значения сохраняются вместе с generated-базой в метаданных версии. У старых прогонов IR может
отсутствовать: он не восстанавливается задним числом из XML как будто это ответ модели.
Контракт и ограничения — [generation-quality](generation-quality.md).

Частичный уникальный индекс PostgreSQL не допускает больше одного активного прогона на проект;
`waiting` считается активным (миграция `0019_technical_questions` пересоздаёт индекс с
`queued`, `running`, `waiting`).
После перезапуска новые незавершённые прогоны с хешем источников повторяются с тем же ID
не более двух раз; опубликованная версия повторно не создаётся. Старые запуски и исчерпавшие
лимит получают failed ([ADR-0008](../adr/0008-evidence-semantic-review-and-recovery.md)).
Хеш снимка источников (`ingest/context.py:source_snapshot_hash`) добавляет поля дерева
материалов только когда они отличаются от значений после миграции 0016, поэтому прогон,
запущенный до обновления, после рестарта восстанавливается, а не падает с «источники
изменились». Источники сохраняют `warning` и `unreadable_pages` (неполное чтение PDF/Excel, миграция 0013). Источники, застрявшие в
`processing` (фоновый разбор файла не пережил перезапуск), — `failed` с причиной «Разбор файла
прервался из-за перезапуска сервера…»: пользователь загружает файл снова или вписывает текст
вручную. SSE-журнал пока живёт в памяти одного процесса; для законченного прогона API может
восстановить итог из БД.

## Транзакции и конкурентность

По умолчанию каждая операция репозитория — отдельная короткая транзакция. Сценарии, которым
нужна атомарность, берут единицу работы: `async with repos.atomic() as tx:` — все `tx.*`
репозитории работают в одной транзакции PostgreSQL (коммит при выходе, откат при исключении;
вложенный `atomic()` возвращает ту же транзакцию). В in-memory режиме это пустой контекст.

- **Блокировка проекта.** `tx.projects.lock(id)` — `SELECT … FOR UPDATE` строки проекта до конца
  транзакции. Под ней выполняются: выдача номера версии (`add_version`), запуск прогона,
  ручное сохранение схемы и удаление проекта. Поэтому ручное сохранение и прогон (или два
  редактора) получают подряд идущие номера версий и не упираются в `uq_versions_project_number`.
- **Ручное сохранение во время сборки** → `409`: сборка (`mode=build`) строит схему от состояния
  на момент старта, и её версия молча перекрыла бы правку. Анализ (`mode=analyze`) версий не
  создаёт, поэтому ему правка не мешает. Проверка идёт под той же блокировкой, что и запуск прогона.
- **Сверка вопросов** пишет вопросы условно: `questions.apply_reconciled(q, expected_status=…)` —
  `UPDATE … WHERE status = <прочитанный>` только полей сверки (статус, цитата, ответ). Ответ
  аналитика, пришедший между чтением вопросов и записью, не затирается; такой вопрос пропускается.
- **Удаление проекта** — одна транзакция (источники, вопросы, прогоны, версии и вызовы модели
  удаляет БД каскадом `ON DELETE CASCADE`); файлы источников удаляются уже после фиксации.
- **Точечные обновления.** Источник меняется через `sources.patch(id, {поля}, only_status=…)` —
  `UPDATE` только перечисленных полей, без перезаписи строки: фоновый разбор файла не затирает
  название и `active`, изменённые пользователем, а правка текста не «оживляет» источник,
  который тем временем перешёл в другой статус (`409`). Время изменения проекта поднимает
  `projects.touch` — `UPDATE … WHERE updated_at < :at`.

- **Карточки проектов без N+1.** `projects.stats(ids)` возвращает `ProjectStats` (исходные
  источники без ответов и без производных узлов, наличие материала, открытые/решённые вопросы, число версий, дорожки последней версии,
  режим активного прогона) пятью агрегирующими запросами независимо от числа проектов; содержимое
  источников и JSONB старых версий не читается. `runs.last_succeeded_id(project_id)` отдаёт id
  последнего успешного прогона без загрузки `analysis`/`ir`. Список проектов и `detail()` строят
  ответ из этих методов; in-memory реализация считает то же самое по словарям.
- **Старты прогонов** сериализуются замком на проект (внутри процесса); между проектами они не
  ждут друг друга, а общий предел параллельных прогонов задаёт семафор исполнения.
- **База ручных правок.** Контекст прогона догружает полный XML ближайшей generated-версии старше
  головы: без неё `ManualPolicy.compare` не видит, что изменил человек. Сверка и вопросы по
  ручным конфликтам под блокировками проекта и источников читают только последнюю версию
  (`versions.latest`) или список без XML.

## Запуск и миграции

Для обычной работы достаточно:

```sh
make up
```

Compose ждёт готовности БД, приложение выполняет `alembic upgrade head`, а `/health` проверяет
соединение. Состояние контейнеров и логи:

```sh
docker compose ps
docker compose logs backend db
```

Для разработки backend вне контейнера задайте `DATABASE_URL` на `localhost:5433` (значение есть в
`.env.example`) и запустите БД через `docker compose up -d db`. `make db-upgrade` читает этот же URL
из корневого `.env`. Отдельное применение миграций:

```sh
make db-upgrade
```

Схему меняйте только новой миграцией; уже применённые файлы не редактируйте. После волны 2
голова схемы — `0023_reviewer_role` (ссылка проверки: роль `reviewer`, область-дорожки,
токен проверки и провенанс ответа по ссылке; индексы FK, безопасный откат); `0022_merge_wave2_heads` объединила ветки
стоимости/техвопросов/ключей и провенанса ответа агента. Волна 2 добавила миграции:
`0018_llm_call_cost` (стоимость прогона, кеш-токены), `0019_technical_questions`
(технические вопросы и `waiting`; при откате ожидающие прогоны переводятся в `failed`),
`0020_user_credentials` (ключи по типам задач; legacy `user_llm_credentials` остаётся),
`0021_agent_answer_provenance` (провенанс ответа агента). Ветка агентного режима волны 4
добавляет `0024_agent_search` (FTS-индекс источников, `down_revision=0022_merge_wave2_heads`).
При интеграции параллельные головы объединяются merge-миграцией (`alembic merge`), а не
перенумерацией. Создать заготовку:

```sh
cd backend && uv run alembic revision --autogenerate -m "описание изменения"
```

Проверьте сгенерированный файл, дополните операции при необходимости и прогоните `make verify`.
Удаление volume тестовой среды необратимо:

```sh
docker compose down -v
```

В production пароль БД и API-ключи задаются отдельно в `/home/deploy/arkhitektor/shared/.env`. Production
Compose откажется запускаться без `POSTGRES_PASSWORD`; значения из `.env.example` на сервере
использовать нельзя.

## Компактная история версий (ADR-0007)

Миграция `0011_compact_versions` добавляет `packed_xml`, `xml_sha256`, `base_version_id`,
`storage_depth`; старый `bpmn_xml` становится nullable. Старые записи остаются читаемыми.
Новые записи хранят сжатый снимок или точную замену диапазона предыдущего XML (формат v1).
Генерация модели и каждая 21-я ручная правка дают независимый снимок; большая дельта также
заменяется снимком. Чтение проверяет SHA-256, номера, глубину и принадлежность одному проекту.
Внешние API, идентификаторы, номера версий и XML-экспорт сохраняются. История не удаляется.

После резервного копирования старые снимки можно перевести в компактный формат:

```sh
uv run --directory backend python -m app.infra.version_maintenance --batch-size 100
```

Команда использует штатный `DATABASE_URL`, обрабатывает каждый пакет одной транзакцией под
блокировкой проекта. Её можно прервать и повторить: завершённые пакеты не обрабатываются снова.
Она не запускает сид и не меняет статусы прогонов. Новые версии сразу записываются компактно.
На VM команда выполняется в backend-контейнере релиза, резервная копия делается заранее.
Освободившееся место PostgreSQL переиспользует после autovacuum; размер файла таблицы не обязан
сразу уменьшиться. Принудительный `VACUUM FULL` для обычного перехода не нужен.

### Сессии правок и контрольные точки (ADR-0010)

Ручное сохранение того же автора вливается в последнюю версию (`manual`, не контрольная точка,
без зависимых, пауза < `VERSION_SESSION_IDLE_SEC`, сессия < `VERSION_SESSION_MAX_SEC`): под
блокировкой проекта строка заменяется новой с тем же номером и новым id. Прогон всегда создаёт
новую версию. `trace`/`report` ручной версии, равные предшественнику, не хранятся
(`trace_inherited`, `report_inherited`): чтение берёт их у ближайшей старшей строки-владельца.
`GET /projects/{id}/versions` отдаёт страницы без XML и JSONB (`lint_count`, `assumption_count`
хранятся колонками). Миграция — `0015_version_sessions`.

Перед откатом на релиз до `0011` остановите записывающий backend и выполните кодом нового релиза:

```sh
uv run --directory backend python -m app.infra.version_maintenance --restore
```

Восстановление идёт от новых записей к старым, также пакетно и повторяемо. После завершения можно
запускать прежнее приложение. Для downgrade Alembic восстановление обязательно: миграция явно
отказывается удалять столбцы с данными компактных версий. Обновлённый `scripts/deploy.sh` перед автоматическим откатом на старый формат выполняет
такое восстановление. При ошибке восстановления откат останавливается, данные сохраняются.

## Квитанции удаления

`deleted_project_access` содержит только хеш доступа и срок действия (30 дней).
Каскад проекта удаляет данные полностью; квитанция остаётся для безопасного сообщения 410.
Миграция — `0012_deleted_project_access`, правила — [ADR-0009](../adr/0009-project-deletion-and-leaving.md).
