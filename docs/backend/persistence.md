# PostgreSQL и миграции

Локальный Compose поднимает PostgreSQL 16 и автоматически применяет Alembic-миграции при старте
backend. Данные БД лежат в Docker volume `postgres_data`, загруженные документы и аудио — в
`uploads_data` (`/data/uploads`). Обычные `docker compose down` и пересборка контейнеров эти данные
не удаляют. `docker compose down -v` удаляет оба volume вместе с данными.

## Что сохраняем

- `projects` — название, описание и даты изменения.
- `sources` — текст, тип и статус источника, метаданные загрузки, ключ файла в volume и место
  для кэшированного дайджеста.
- `questions` — статус, важность, текст, цитаты-доказательства, ответ и элементы BPMN. Один
  answer-источник может быть связан только с одним вопросом.
- `runs` — режим, статус/этап/прогресс, сводка вопросов, снимки анализа и структуры, отчёт,
  модель, время выполнения, ошибка и ссылка на созданную версию.
- `diagram_versions` — BPMN XML, происхождение, номер, diff, отчёт проверки, цитаты и дорожки.
  Один прогон может создать не более одной версии; ссылки прогона и версии проверяются внешними
  ключами.
- `llm_calls` — запрос и результат каждого этапа пайплайна, этап и задержка. Провайдер пока не
  сообщает единый формат токенов, поэтому `tokens_in`/`tokens_out` остаются `null`.

Нормализованный JSON IR будет заполняться после реализации принятой RFC-структуры IR. Сейчас
пайплайн возвращает готовый BPMN-черновик, поэтому поле `runs.ir` сохраняется пустым, вместо того
чтобы выдавать XML за промежуточное представление.

Удаление проекта удаляет связанные записи и файлы. Частичный уникальный индекс PostgreSQL не допускает
больше одного активного прогона на проект. После перезапуска незавершённые прогоны получают статус
ошибки, чтобы интерфейс не оставался в бесконечном ожидании. SSE-журнал пока живёт в памяти одного
процесса; для законченного прогона API может восстановить итог из БД.

## Запуск и миграции

Для обычной работы достаточно:

```sh
make up
```

Compose ждёт готовности БД, приложение выполняет `alembic upgrade head`, а `/health` проверяет
соединение. Состояние контейнеров и логи:

```sh
docker compose ps
docker compose logs backend db
```

Для разработки backend вне контейнера задайте `DATABASE_URL` на `localhost:5433` (значение есть в
`.env.example`) и запустите БД через `docker compose up -d db`. `make db-upgrade` читает этот же URL
из корневого `.env`. Отдельное применение миграций:

```sh
make db-upgrade
```

Схему меняйте только новой миграцией; уже применённые файлы не редактируйте. Текущая голова схемы —
`0004_persistence_relationships`. Создать заготовку:

```sh
cd backend && uv run alembic revision --autogenerate -m "описание изменения"
```

Проверьте сгенерированный файл, дополните операции при необходимости и прогоните `make verify`.
Удаление volume тестовой среды необратимо:

```sh
docker compose down -v
```

В production пароль БД и API-ключи задаются отдельно в `/home/deploy/arkhitektor/shared/.env`. Production
Compose откажется запускаться без `POSTGRES_PASSWORD`; значения из `.env.example` на сервере
использовать нельзя.
