# PostgreSQL и миграции

Локальный Compose поднимает PostgreSQL 16 и автоматически применяет Alembic-миграции при старте
backend. Данные БД лежат в Docker volume `postgres_data`, загруженные документы и аудио — в
`uploads_data` (`/data/uploads`). Обычные `docker compose down` и пересборка контейнеров эти данные
не удаляют. `docker compose down -v` удаляет оба volume вместе с данными.

## Что сохраняем

- `projects` — название, описание и даты изменения.
- `sources` — текст, тип и статус источника, метаданные загрузки, ключ файла в volume и место
  для кэшированного дайджеста.
- `questions` — статус, важность, текст, цитаты-доказательства, ответ и элементы BPMN. Один
  answer-источник может быть связан только с одним вопросом.
- `runs` — режим, статус/этап/прогресс, сводка вопросов, снимки анализа и структуры, отчёт,
  модель, время выполнения, ошибка, предупреждения (`warnings`: например, контекст модели был
  обрезан) и ссылка на созданную версию.
- `diagram_versions` — BPMN XML, происхождение, номер, diff, отчёт проверки, цитаты и дорожки.
  Один прогон может создать не более одной версии; ссылки прогона и версии проверяются внешними
  ключами.
- `llm_calls` — запрос и результат каждого этапа пайплайна, этап, задержка и токены
  (`tokens_in`/`tokens_out` — сумма по всем запросам этапа из поля `usage` провайдера; у mock
  остаются `null`). Запрос хранится в компактном виде: вместо текстов источников и XML — их `id`,
  длина и SHA-256 (`ingest/context.py:describe_context`). Так таблица не раздувается копиями
  документов на каждый вызов, а по хешу видно, какая версия текста была у модели; сами тексты
  лежат в `sources`.

- `user_onboarding` и `user_onboarding_items` (миграция `0008_onboarding`) — состояние тура
  (статус, шаг, учебный проект), скрыт ли чек-лист «Начало работы» и отмеченные пункты чек-листа
  (`PRIMARY KEY (user_id, item_key)`, отметка `INSERT … ON CONFLICT DO NOTHING`: повтор не меняет
  `completed_at`). Строка `user_onboarding` создаётся лениво при первом обращении; удаление
  пользователя убирает обе таблицы (`CASCADE`), удаление учебного проекта обнуляет
  `tour_project_id` (`SET NULL`). Устройство — [onboarding.md](onboarding.md).
- `runs.created_by` — кто запустил прогон (`SET NULL` при удалении пользователя): прогон
  завершается в фоне, и по этому полю чек-лист отмечает `diagram_built` и `diagram_rebuilt`
  тому, кто запустил, а не владельцу проекта. `0008` откатывается `alembic downgrade -1`.

Сгенерированные прогоны сохраняют нормализованный GraphIR v1 в `runs.ir`, анализ и результат
проверки — в отдельных JSON-полях. XML строит компилятор; ручная семантика и её защищённые
значения сохраняются вместе с generated-базой в метаданных версии. У старых прогонов IR может
отсутствовать: он не восстанавливается задним числом из XML как будто это ответ модели.
Контракт и ограничения — [generation-quality](generation-quality.md).

Частичный уникальный индекс PostgreSQL не допускает больше одного активного прогона на проект.
После перезапуска незавершённые прогоны получают статус ошибки, а источники, застрявшие в
`processing` (фоновый разбор файла не пережил перезапуск), — `failed` с причиной «Разбор файла
прервался из-за перезапуска сервера…»: пользователь загружает файл снова или вписывает текст
вручную. SSE-журнал пока живёт в памяти одного процесса; для законченного прогона API может
восстановить итог из БД.

## Транзакции и конкурентность

По умолчанию каждая операция репозитория — отдельная короткая транзакция. Сценарии, которым
нужна атомарность, берут единицу работы: `async with repos.atomic() as tx:` — все `tx.*`
репозитории работают в одной транзакции PostgreSQL (коммит при выходе, откат при исключении;
вложенный `atomic()` возвращает ту же транзакцию). В in-memory режиме это пустой контекст.

- **Блокировка проекта.** `tx.projects.lock(id)` — `SELECT … FOR UPDATE` строки проекта до конца
  транзакции. Под ней выполняются: выдача номера версии (`add_version`), запуск прогона,
  ручное сохранение схемы и удаление проекта. Поэтому ручное сохранение и прогон (или два
  редактора) получают подряд идущие номера версий и не упираются в `uq_versions_project_number`.
- **Ручное сохранение во время сборки** → `409`: сборка (`mode=build`) строит схему от состояния
  на момент старта, и её версия молча перекрыла бы правку. Анализ (`mode=analyze`) версий не
  создаёт, поэтому ему правка не мешает. Проверка идёт под той же блокировкой, что и запуск прогона.
- **Сверка вопросов** пишет вопросы условно: `questions.apply_reconciled(q, expected_status=…)` —
  `UPDATE … WHERE status = <прочитанный>` только полей сверки (статус, цитата, ответ). Ответ
  аналитика, пришедший между чтением вопросов и записью, не затирается; такой вопрос пропускается.
- **Удаление проекта** — одна транзакция (источники, вопросы, прогоны, версии и вызовы модели
  удаляет БД каскадом `ON DELETE CASCADE`); файлы источников удаляются уже после фиксации.
- **Точечные обновления.** Источник меняется через `sources.patch(id, {поля}, only_status=…)` —
  `UPDATE` только перечисленных полей, без перезаписи строки: фоновый разбор файла не затирает
  название и `active`, изменённые пользователем, а правка текста не «оживляет» источник,
  который тем временем перешёл в другой статус (`409`). Время изменения проекта поднимает
  `projects.touch` — `UPDATE … WHERE updated_at < :at`.

## Запуск и миграции

Для обычной работы достаточно:

```sh
make up
```

Compose ждёт готовности БД, приложение выполняет `alembic upgrade head`, а `/health` проверяет
соединение. Состояние контейнеров и логи:

```sh
docker compose ps
docker compose logs backend db
```

Для разработки backend вне контейнера задайте `DATABASE_URL` на `localhost:5433` (значение есть в
`.env.example`) и запустите БД через `docker compose up -d db`. `make db-upgrade` читает этот же URL
из корневого `.env`. Отдельное применение миграций:

```sh
make db-upgrade
```

Схему меняйте только новой миграцией; уже применённые файлы не редактируйте. Текущая голова схемы —
`0011_compact_versions` (после объединения авторства/онбординга в `0010_merge_heads`). Создать заготовку:

```sh
cd backend && uv run alembic revision --autogenerate -m "описание изменения"
```

Проверьте сгенерированный файл, дополните операции при необходимости и прогоните `make verify`.
Удаление volume тестовой среды необратимо:

```sh
docker compose down -v
```

В production пароль БД и API-ключи задаются отдельно в `/home/deploy/arkhitektor/shared/.env`. Production
Compose откажется запускаться без `POSTGRES_PASSWORD`; значения из `.env.example` на сервере
использовать нельзя.

## Компактная история версий (ADR-0007)

Миграция `0011_compact_versions` добавляет `packed_xml`, `xml_sha256`, `base_version_id`,
`storage_depth`; старый `bpmn_xml` становится nullable. Старые записи остаются читаемыми.
Новые записи хранят сжатый снимок или точную замену диапазона предыдущего XML (формат v1).
Генерация модели и каждая 21-я ручная правка дают независимый снимок; большая дельта также
заменяется снимком. Чтение проверяет SHA-256, номера, глубину и принадлежность одному проекту.
Внешние API, идентификаторы, номера версий и XML-экспорт сохраняются. История не удаляется.

После резервного копирования старые снимки можно перевести в компактный формат:

```sh
uv run --directory backend python -m app.infra.version_maintenance --batch-size 100
```

Команда использует штатный `DATABASE_URL`, обрабатывает каждый пакет одной транзакцией под
блокировкой проекта. Её можно прервать и повторить: завершённые пакеты не обрабатываются снова.
Она не запускает сид и не меняет статусы прогонов. Новые версии сразу записываются компактно.
На VM команда выполняется в backend-контейнере релиза, резервная копия делается заранее.
Освободившееся место PostgreSQL переиспользует после autovacuum; размер файла таблицы не обязан
сразу уменьшиться. Принудительный `VACUUM FULL` для обычного перехода не нужен.

Перед откатом на релиз до `0011` остановите записывающий backend и выполните кодом нового релиза:

```sh
uv run --directory backend python -m app.infra.version_maintenance --restore
```

Восстановление идёт от новых записей к старым, также пакетно и повторяемо. После завершения можно
запускать прежнее приложение. Для downgrade Alembic восстановление обязательно: миграция явно
отказывается удалять столбцы с данными компактных версий. Обновлённый `scripts/deploy.sh` перед автоматическим откатом на старый формат выполняет
такое восстановление. При ошибке восстановления откат останавливается, данные сохраняются.
