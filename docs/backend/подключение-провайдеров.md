# Подключение LLM-помощника и распознавания речи

Ключи провайдеров хранятся только в корневом `.env`. Файл игнорируется Git и не должен
попадать в коммиты, скриншоты или клиентский JavaScript. Перед отправкой документов во внешний
LLM-провайдер убедитесь, что в них нет персональных и конфиденциальных данных.

1. Скопируйте `.env.example` в `.env` в корне репозитория.
2. Для любого провайдера с OpenAI-compatible Chat Completions укажите
   `LLM_PROVIDER=openai_compatible`, `LLM_API_KEY`, `LLM_BASE_URL` и `LLM_MODEL`. Меняя эти
   четыре значения, можно перейти на другую подходящую модель без изменения кода. Для серверов,
   которые не поддерживают `response_format: {type: json_object}`, задайте `LLM_JSON_MODE=false`;
   инструкции модели всё равно требуют JSON, а приложение проверяет его перед дальнейшей работой.
   JSON-запросы (анализ и сборка) идут с `temperature=LLM_JSON_TEMPERATURE`, по умолчанию `0`:
   при дефолтной температуре DeepSeek (1.0) модель изредка отвечает не по схеме и прогон падает.
   Чат помощника использует температуру провайдера по умолчанию.
   `LLM_JSON_MAX_TOKENS` задаёт бюджет JSON-ответа (по умолчанию `16384`); чат — `4096`.
   Проверка подробных регламентов показала, что граф с 44–49 узлами и дословными основаниями
   может не помещаться в прежние `8192`. Лимит не требует выдать столько токенов и не снимает
   общий deadline; `finish_reason=length` по-прежнему отклоняется.
   Если модель ограничивает выход сильнее, согласуйте это значение с её API. Ответ,
   остановленный по `finish_reason=length`, не считается полным успешным JSON.
   `LLM_PROVIDER=deepseek` и переменные `DEEPSEEK_*` временно сохранены для старого production `.env`.
   Backend ждёт ответ до `LLM_TIMEOUT_SEC`. Временные сбои (HTTP 408/429/5xx, таймаут, обрыв
   сети) повторяются до `LLM_MAX_RETRIES` раз с экспоненциальной паузой от `LLM_RETRY_BASE_SEC`
   до `LLM_RETRY_MAX_SEC` и
   джиттером; заголовок `Retry-After` учитывается (не больше 30 секунд и не дольше срока
   прогона). Таймаут чтения запрос уже отправлен и оплачен, поэтому повторяется не более одного
   раза; отказы до отправки (обрыв соединения, 429, 5xx) повторяются до лимита. Весь прогон ограничен `RUN_DEADLINE_SEC`, а
   размер порций анализа/бюджет структуры — `LLM_CONTEXT_BUDGET_CHARS`. Анализ вопросов
   проходит весь доступный снимок порциями и отдельным проверочным запросом; структура пока
   использует ограниченный текст с предупреждением об обрезке. Токены всех запросов одного
   этапа суммируются в `llm_calls`. Это может увеличить число запросов на больших проектах;
   общий лимит вопросов не вводится. Подробности — [правила генерации](generation-quality.md).
3. Перезапустите локальный backend (`make up` для Compose либо перезапуск dev-сервера).
   Compose передаёт generic `LLM_*` и legacy `DEEPSEEK_*`; внутренний `bpmn-tools` подключается
   автоматически. Для dev-backend запустите `make dev-bpmn-tools` и задайте
   `BPMN_TOOLS_URL=http://localhost:3000`, иначе доступен только ограниченный локальный mock.
4. Откройте серверный проект, задайте вопрос помощнику и проверьте ответ.

Для голосовой расшифровки отдельно укажите `STT_PROVIDER=deepgram` и новый `DEEPGRAM_API_KEY`.
Ключи можно добавить только локально в `.env`; не вставляйте их в исходники, GitLab или чат.
Успешно обработанная запись без распознанной речи возвращает `422`, код `NO_SPEECH` и
приглашение записать снова. Это ожидаемый результат: интерфейс показывает уведомление и
сохраняет текстовый черновик. Сбой провайдера и повреждённый ответ не маскируются под молчание.

Для серверного проекта endpoint принимает его id, вопрос, последние сообщения диалога и актуальный
BPMN XML. Backend сам загружает название, описание, активные источники и открытые вопросы проекта.
Для локального черновика браузер отправляет его заголовок, исходное описание и текущую схему только
в момент вопроса; backend не сохраняет этот черновик. Контекст ограничен по объёму. Модель
консультирует и предлагает изменения, но не редактирует схему.
