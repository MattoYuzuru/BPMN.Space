# Деплой на демо-VM

Текущая production-схема — Ubuntu 24.04, Docker Compose, Caddy на портах 80 и 443, FastAPI, PostgreSQL 16 и Node `bpmn-tools` во внутренней сети Compose. Runtime layout/lint не публикует порт наружу; backend ждёт его healthcheck. Для `bpmn.space` и `www.bpmn.space` Caddy автоматически получает и обновляет TLS-сертификаты Let's Encrypt. Данные сертификатов сохраняются в volumes `caddy_data` и `caddy_config`. PostgreSQL хранит состояние проектов в volume `postgres_data`, загруженные документы — в `uploads_data`. Деплой отправляет архив проверенного Git-коммита по SSH; VM не нужен доступ к приватному GitLab. GitLab CI/CD не используется.

## Один раз: подготовить VM

1. Установите Ubuntu 24.04 и разрешите входящий TCP 22, 80 и 443 в сетевых правилах Selectel. Порт 80 нужен для перенаправления на HTTPS и проверки владения доменом Let's Encrypt; порт 443 обслуживает сайт. Порт 8000 наружу не открывайте.
2. Каждый участник создаёт собственную пару SSH-ключей на своём компьютере, например `ssh-keygen -t ed25519 -C "имя-участника" -f ~/.ssh/arkhitektor_deploy`. На VM передаётся только публичный файл `~/.ssh/arkhitektor_deploy.pub`; приватный ключ остаётся у владельца.
3. Скопируйте bootstrap-скрипт на VM и один раз запустите его от `root`:

   ```bash
   scp scripts/bootstrap-vm.sh root@<IP_VM>:/root/bootstrap-vm.sh
   ssh root@<IP_VM> 'bash /root/bootstrap-vm.sh'
   ```

4. Каждый участник отправляет администратору только **публичный** файл `.pub`. Администратор добавляет ключ в аккаунт `deploy`:

   ```bash
   cat ~/.ssh/<имя_публичного_ключа>.pub | ssh root@<IP_VM> 'cat >> /home/deploy/.ssh/authorized_keys && chown deploy:deploy /home/deploy/.ssh/authorized_keys && chmod 0600 /home/deploy/.ssh/authorized_keys'
   ```

   После настройки проверьте вход: `ssh deploy@<IP_VM>`. Пользователь `deploy` включён в группу `docker`, а значит имеет права уровня root: выдавайте SSH-доступ только доверенным членам команды.

## Один раз: положить секреты на VM

В корне локальной копии создайте `.env` из `.env.example` и добавьте ключи провайдеров. Локальный Compose использует `POSTGRES_PASSWORD=local-dev-only`. Для VM отдельно задайте `DEPLOY_POSTGRES_PASSWORD` случайным значением длиной не менее 32 символов, например результатом `openssl rand -hex 32`. Production пароль должен оставаться неизменным между релизами: изменение переменной Compose само по себе не меняет пароль уже созданного пользователя PostgreSQL. Отдельная переменная не меняет доступ к существующей локальной БД.

`upload-server-env.sh` отправляет production-переменные по SSH в `/home/deploy/arkhitektor/shared/.env`, выставляет права `0600` и не сохраняет секреты в релизах или Git. Путь находится в домашнем каталоге `deploy`, поэтому пользователь может переключать релизы без root-прав.

```bash
DEPLOY_HOST=<IP_VM> scripts/upload-server-env.sh
```

Запускает её один администратор с актуальными ключами. Не пересылайте `.env` команде и не вставляйте значения ключей в команды, issue или сообщения. После загрузки значения не отображаются.

## Каждый релиз

1. Изменения должны попасть в `main` через Merge Request, а локальная копия должна быть чистой и обновлённой.
2. Выполните `make verify`; проверьте отчёт и SHA коммита.
3. Убедитесь, что `DEPLOY_HOST` указывает на VM команды, и выданы права SSH вашему публичному ключу.
4. Запустите с SHA коммита, который уже находится в `origin/main`:

   ```bash
   DEPLOY_HOST=<IP_VM> scripts/deploy.sh <commit-sha>
   ```

Скрипт архивирует коммит из Git, передаёт его по SSH в `/home/deploy/arkhitektor/releases/<sha>`, собирает Compose-образы на VM и переключает `current`. Перед релизом, если предыдущая версия использует PostgreSQL, он сохраняет `pg_dump` и архив `uploads_data` в `/home/deploy/arkhitektor/backups/<UTC-время>-<sha>` с правами `0700/0600`. На первой установке, когда предыдущей версии с БД нет, бэкап пропускается.

При старте backend выполняет `alembic upgrade head`; Compose ждёт готовности PostgreSQL и затем backend healthcheck. Скрипт ждёт `/health` до двух минут и при ошибке возвращает предыдущий код приложения. Docker volumes остаются на месте.

Версии начиная с миграции `0011_compact_versions` используют компактный XML. Откат на более старый
релиз требует предварительного `python -m app.infra.version_maintenance --restore` кодом нового
релиза при остановленных записях (см. `docs/backend/persistence.md`, ADR-0007). Скрипт деплоя этого релиза перед автоматическим откатом
останавливает backend и восстанавливает XML кодом нового релиза, подключённым read-only в контейнер.
Если восстановление не прошло, он останавливает откат и сохраняет данные для ручного разбора.

Перед релизом, который меняет схему уже используемой БД, проверьте совместимость миграции с предыдущей версией приложения. Скрипт деплоя откатывает код, но не откатывает схему БД и не восстанавливает данные из бэкапа. Резервные копии остаются вне каталога релизов; контролируйте свободное место и переносите копии с VM для долговременного хранения. Старый релиз стартует поверх более новой схемы, если миграции аддитивные (новые таблицы и nullable-колонки): при старте он видит неизвестную ревизию БД, пишет предупреждение «Схема БД новее этого релиза» и пропускает `alembic upgrade`, а не падает. Неаддитивные миграции (удаление, переименование, `NOT NULL` без значения по умолчанию) так откатить нельзя. Первая установка создаёт пустой volume БД и загружает демо-данные; прежнее in-memory состояние приложения восстановить нельзя.

## Проверка и восстановление

Откройте `https://bpmn.space/` и `https://www.bpmn.space/`, затем проверьте, что `http://bpmn.space/` перенаправляет на HTTPS и страница показывает действующий сертификат. `/health` доступен для проверки через домен. Не используйте `docker compose down -v`: команда удаляет volume PostgreSQL, пользовательские файлы и данные Caddy. Диагностика на VM:

```bash
ssh deploy@<IP_VM> 'cd /home/deploy/arkhitektor/current && docker compose --env-file /home/deploy/arkhitektor/shared/.env -p arkhitektor -f compose.yaml -f compose.prod.yaml ps'
ssh deploy@<IP_VM> 'cd /home/deploy/arkhitektor/current && docker compose --env-file /home/deploy/arkhitektor/shared/.env -p arkhitektor -f compose.yaml -f compose.prod.yaml logs --tail=100'
```

Если сертификат не выпущен, проверьте A-записи для `bpmn.space` и `www.bpmn.space`, доступность входящих TCP 80/443 и логи Caddy. Выпуск сертификата выполняется автоматически после старта релиза с доменной конфигурацией; вручную передавать сертификаты или менять production `.env` не требуется.

Вход в аккаунт в production требует HTTPS: cookie сессии получает флаг `Secure`, и по обычному HTTP браузер её не примет. На стенде без HTTPS задайте `SESSION_COOKIE_SECURE=false` в серверном окружении; после подключения HTTPS уберите эту строку. Не используйте production-ключи с публичным адресом без ограничений доступа.
