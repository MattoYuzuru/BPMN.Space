# План готовности к полуфиналу и следующей итерации

Обновлено 4 октября 2026. Это рабочий план, основанный на требованиях полуфинала,
RFC Матвея (`docs/rfc/0001-architecture.md`), стайлгайде и текущем коде. Работа ведётся
в локальной ветке `research/model-provider-and-diagram-style`; публикации на сервер нет.

## Что требует полуфинал

- Принять текст описания процесса.
- Показать участников, последовательность действий и ветвления.
- Выдать валидный BPMN 2.0 XML, который открывается и редактируется в bpmn.io.
- Показать исходный текст и схему, в том числе процесс с несколькими участниками и ветвлением.
- Подготовить исходный код, инструкцию запуска, примеры входа/результата и описание возможностей
  и ограничений.
- Модель можно вызывать через API. Локальное исполнение не обязательно. В финале будут модели
  Яндекса, поэтому провайдер должен заменяться конфигурацией без переписывания бизнес-процесса.

## Последовательность работ

### 1. Проверить локальные изменения доступа

1. Запустить миграции и Postgres-тесты.
2. Проверить единый набор срока ссылки для двух ролей: 7 дней, 30 дней, год, бессрочно.
3. Пройти viewer-ссылку как гость и как авторизованный пользователь; во втором случае проект
   должен сохраниться в общем списке после принятия.
4. Пройти editor-ссылку без аккаунта и с аккаунтом; без сессии редактирование недоступно.
5. Проверить, что принятие viewer не понижает уже существующее editor-членство, а отзыв
   ссылки и удаление членства — отдельные действия.

### 2. Довести генерацию до требований полуфинала

1. Утвердить Pydantic IR с участниками, задачами, событиями, шлюзами, направленными потоками,
   условиями и ссылками на источники. Ограничить enum типов и длины, не принимать XML из LLM.
2. Проверять каждую цитату по исходнику и отмечать извлечённое отдельно от допущений.
3. Скомпилировать IR в ProcessGraph, затем программно построить BPMN XML.
4. Добавить проверку графа: единственный старт/завершение в базовом сценарии, достижимость узлов,
   корректные входы/выходы шлюзов, именованные условия, отсутствие висячих sequence flow.
5. Валидировать XSD, bpmnlint и импорт/экспорт bpmn-js. На ошибку — ограниченное исправление
   IR с диагностикой; после лимита дать пользователю понятную ошибку и исходный этап сбоя.
6. Реализовать layout для нескольких дорожек и XOR/AND ветвей; не терять ручные правки логики
   при следующей генерации.
7. Добавить тест-кейсы: простой процесс, два пула участников и message flow, XOR с обоими путями, параллельная работа,
   неполные источники с явным допущением, противоречивые источники, кривой ответ провайдера.

### 3. Проверить заменяемость модели

1. Оставить `ProcessPipeline` контрактом приложения, а провайдера выбирать из настроек окружения.
2. Для каждого API явно задавать совместимость: Chat Completions, endpoint, auth header,
   JSON Schema/JSON mode, лимит контекста, параметры sampling. Не обещать универсальную
   совместимость с API, который не реализует этот контракт.
3. Отдельно проверить финального Yandex-провайдера. Если он не полностью Chat Completions,
   добавить второй адаптер под тот же внутренний контракт, не трогая сервисы и BPMN-компилятор.
4. Хранить ключи только в локальном `.env`/секретах сервера; smoke-test провести с разрешённым
   провайдером и лимитом расходов перед серверной выкладкой.

### 4. Ограниченная визуальная выразительность

1. Базовая схема остаётся нейтральной. Подсвечивать только смысловые маркеры из закрытого набора:
   допущение — янтарный, ключевая развилка/выбранный фокус — синий, подтверждённый результат —
   хвойный. Ошибка — сурик только для ошибок, не для важности.
2. Цвет выбирает детерминированное правило по типу/статусу элемента после валидации IR; модель
   не присылает произвольные hex-коды. Значение продублировать подписью, типом или маркером,
   чтобы смысл не зависел только от цвета.
3. Для формы ориентироваться на структуру графа: последовательность — ровные дорожки, XOR —
   читаемое расхождение/слияние, AND — параллельные дорожки, цикл — короткая обратная связь.
   Не выбирать форму случайно и не превращать всю схему в цветную.
4. Пробник `docs/research/semantic-style/decision-with-assumption.bpmn` показывает
   развилку, две дорожки и ограниченные смысловые цвета. Это эксперимент, не пример для жюри:
   перед переносом в продукт проверить
   импорт bpmn.io, контраст в двух темах, читаемость на длинных русских подписях и сохранение
   цветов после ручного сохранения.

### 5. Владение данными и выпуск

1. До финального запуска снять инвентаризацию проектов без владельца и членств; ничего не удалять.
2. Сопоставить проекты с владельцами, сохранить backup БД и файлов, подготовить точный перечень
   кандидатов на удаление и отдать его владельцу продукта на проверку.
3. После проверки проекта пользователем: прогнать `make check`, миграции на копии/стенде,
   проверку OpenAPI-контрактов и smoke-тесты login/share/upload/generation.
4. Только после отдельного согласования конкретного релиза — вливать и выкладывать; затем
   проверить health, HTTPS, миграции, контейнеры и контрольную схему на сервере.

## Что уже проверено в этой локальной итерации

- Увеличено минимальное число символов пароля с 12 до 8.
- Провайдер DeepSeek выделен в OpenAI-compatible Chat Completions адаптер с настраиваемой
  базой URL, моделью, JSON mode и повторными попытками; старые настройки сохранены.
- Viewer-ссылки теперь можно принять в аккаунт и увидеть проект в списке; editor-ссылка требует
  входа для принятия.
- Для viewer и editor выровнены сроки: 7 дней, 30 дней, год, бессрочно (`0` дней); пропуск срока
  сохраняет прежнее поведение по умолчанию в 30 дней.
- Живые LLM/STT-вызовы и действия с production-проектами/секретами не выполнялись.
