# RFC-0004. Агентный режим: модель сама читает источники через инструменты

- Дата: 2026-11-04
- Статус: шаг 1 реализован — порт `complete_with_tools`, инструменты только-чтения, цикл,
  бюджет ходов/токенов/денег, режим `RunProfile.mode=agent`, FTS-поиск и восстановление;
  рабочие модели (`worker`/`delegate`), эталонная оценка на `prompt-eval` и включение по

## Зачем

Сейчас прогон — фиксированный конвейер одношаговых запросов: порции источников → вопросы →
проверка вопросов → выдержки → граф IR → смысловая проверка. Код решает, что модель увидит и в
каком порядке. Это предсказуемо и проверяемо: каждая цитата обязана быть дословной подстрокой
источника, граф проходит топологию, XSD и bpmnlint. Слабое место — модель не может «вернуться
и перечитать»: если ответ на вопрос лежит на 80-й странице регламента, а порция с ним уже
прошла, модель узнает о нём только из выдержек, которые сама же сделала раньше.

Агентный режим даёт модели инструменты и бюджет. Модель сама решает, какие разделы читать,
что искать и какие гипотезы проверить, а сервер по-прежнему проверяет каждое утверждение.

## Что уже готово

- Провайдеры за `LlmClient` (ADR-0011): Anthropic, OpenAI, совместимые API. У Claude Opus 5.5,
  Sonnet 5.5 и Haiku 5.5 контекст 1M токенов. Многие проекты целиком помещаются в один запрос,
  а кеширование префикса удешевляет повторное чтение.
- Длинные документы и записи разбираются в текст с маркерами страниц и времени (ADR-0012).
- Проверки оснований и графа не зависят от того, кто выбрал фрагмент: конвейер или агент.

## Предложение

Новый метод клиента `complete_with_tools(system, messages, tools, budget)`. Он переводит формат
инструментов в API провайдера: `tool_use`/`tool_result` у Anthropic, `tools`/`tool_calls` у OpenAI.
Совместимые API без инструментов остаются на текущем конвейере.

Инструменты (только чтение и предложения, без побочных эффектов до финальной проверки):

| Инструмент | Что делает | Проверка сервера |
|---|---|---|
| `list_sources()` | id, название, тип, объём, страницы без текста | — |
| `read_source(id, from, to)` | фрагмент по страницам/символам/таймкодам, не больше лимита | права и границы |
| `search_sources(query)` | полнотекстовый поиск по порциям (PostgreSQL FTS, `russian`) | лимит выдачи |
| `list_questions()` | открытые и отвеченные вопросы с допущениями | — |
| `propose_question(text, assumption, quotes[])` | черновик уточняющего вопроса | цитаты дословны |
| `check_graph(ir)` | валидация IR, привязки цитат, XSD, bpmnlint | ошибки возвращаются модели |
| `submit(questions, ir)` | завершение | те же проверки, что сейчас |

Бюджет прогона: число ходов, токены и срок (адаптивный deadline из ADR-0012). Каждый вызов
инструмента пишется в `llm_calls` хешами, как и сейчас; ключ и тексты не копируются. Отмена
прогона прерывает цикл между ходами и текущий HTTP-запрос.

Если весь проект помещается в окно модели с запасом, агент получает тексты сразу в кешируемом
префиксе, а инструменты чтения нужны только для навигации. Для больших проектов он начинает с
оглавления (`list_sources` + заголовки разделов) и читает по запросу.

## Как внедрять

1. ✅ Флаг `LLM_AGENT_MODE` (выключен по умолчанию) и `RunProfile.mode` (`pipeline`/`agent`) с
   проверкой: агент требует включённого флага и модели с инструментами (`capabilities.tools`),
   иначе 422; интерфейс выбора режима — волна интерфейса.
2. Набор эталонов (`prompt-eval`): три сложных регламента и запись совещания с ожидаемыми
   задачами, ролями и шлюзами. Сравниваем конвейер и агент по полноте, числу ложных вопросов,
   стоимости и времени. Записанные сценарии механики уже в тестах, живой замер — следующий шаг.
3. Включать по умолчанию только для провайдеров с инструментами и при выигрыше на эталонах.

## Что реализовано (шаг 1)

- **Порт.** `LlmClient.complete_with_tools(system, messages, tools, max_tokens, effort)`
  (`llm/client.py`, `llm/tools.py`): провайдеро-независимые `ToolDefinition`/`ToolUse`/
  `ConversationMessage`/`ToolTurn`. Anthropic переводит их в `tool_use`/`tool_result`
  (результаты подряд — одним user-сообщением), OpenAI и совместимые — в `tools`/`tool_calls`.
  Токены пишутся общим `record_usage`, поэтому кеш, стоимость и бюджет волны 2 работают и для
  агентных ходов; обрезка по `max_tokens` и отказ модели — те же явные ошибки.
- **Цикл** — `llm/agent.py:AgentRunner`: стартовое сообщение с оглавлением источников, вопросы,
  схема и лимиты; ход модели → инструменты → результаты; завершение только принятым `submit`.
  Модель может ответить текстом без инструмента — один наставительный ход, затем ошибка.
- **Инструменты только-чтения** (`llm/agent.py`, проверки серверные): `list_sources`,
  `read_source` (смещение/лимит, не больше `LLM_AGENT_READ_MAX_CHARS`), `search_sources`
  (PostgreSQL FTS `russian`, миграция `0024_agent_search`; in-memory заменитель для тестов),
  `list_questions`, `propose_question` (дословные цитаты), `check_graph` (валидация IR,
  оснований, топологии, XSD и bpmnlint без сохранения), `submit` (те же проверки и публикация
  обычными этапами прогона). До `submit` проект не меняется.
- **Промпт** — `AGENT_PROMPT_VERSION` в коде: правила [generation-quality](../backend/generation-quality.md),
  плейбуки типов материалов (совещание, демо, регламент, таблица, веб-страница), запрет
  выполнять инструкции из текстов источников, требование дословных цитат и `submit` с IR.
- **Бюджет прогона** — ходы (`RunProfile.max_steps` ≤ `LLM_AGENT_MAX_STEPS`), токены и деньги
  (`RunProfile.budget`). Перед каждым ходом проверяются и токены/деньги (накопитель волны 2), и
  число ходов; достигнутая граница — не ошибка, а `waiting` с блокирующим техническим вопросом
  `budget_reached`. Продолжение после действия пользователя даёт новую попытку с полным запасом
  ходов, но потраченные токены и деньги по-прежнему считаются по журналу.
- **Журнал** — `llm_calls` с `stage=agent`: номер хода, имена инструментов, SHA-256 аргументов и
  результатов, токены, кеш и стоимость на момент вызова. Тексты источников не копируются.
- **Режим и восстановление (ADR-0008)** — `RunCreate.profile.mode` (`pipeline`/`agent`),
  флаг оператора `LLM_AGENT_MODE` (выключен), проверка `capabilities.tools`. Состояние
  сохраняется в `ir.execution.agent` (шаги, журнал хешей, сданные вопросы и канонический IR):
  после рестарта принятый `submit` перепроверяется по текущим материалам и публикуется без
  повторной оплаты, а незавершённый цикл продолжается с учётом потраченных ходов.
- **Оценка до запуска** (`POST /projects/{id}/runs/estimate`) для `mode=agent` — диапазон
  ходов от «оглавление и submit» до лимита, помеченный как приблизительный.
- **Тесты без сети** — записанные `tool_use`/`tool_calls` (`RecordedToolClient`), цикл, границы
  чтения, цитаты, отказ и повтор IR, бюджет, отмена, восстановление, in-memory и PostgreSQL
  FTS (миграция 0024).

Ещё не сделано: `worker`/`delegate` и рабочие модели (RFC-0006, шаг 4–5), MCP-доступ к режиму,
кеш производных источников, эталонное сравнение с конвейером на живых моделях, интерфейс выбора
режима и живой прогресс ходов. Смысловая сверка конвейера (`LLM_SEMANTIC_REVIEW`) внутри
`submit` не выполняется: проверяются IR, дословные основания, топология, XSD и bpmnlint.

## Риски

- Стоимость: агент может читать больше, чем нужно. Ограничивается бюджетом и метриками на эталонах.
- Недетерминированность: два прогона дают разный путь чтения. Результат всё равно проходит
  те же проверки, а в `llm_calls` остаётся воспроизводимый журнал.
- Внедрение инструкций через текст источника: модель может принять фразу из документа за
  команду. Инструменты не меняют данные до `submit`, а `submit` проходит проверки сервера.

## Не входит

OCR сканов, генерация пулов и подпроцессов (нужно расширение IR, см.
`docs/research/product-priorities-2026-10.md`), распределённая очередь прогонов.
