# Проверки агентских изменений

Для хуков нужны `python3` (stdlib, POSIX), Node и обычные инструменты проекта.
Установите зависимости из lockfile (`npm ci`; для одной проверки без prepare —
`npm ci --ignore-scripts`). Biome/Secretlint запускаются только из локального
`node_modules/.bin`: отсутствие инструментов даёт ошибку, а не установку
одноимённого стороннего пакета или другой версии через `npx`.
Контракт событий: [Claude Code hooks](https://code.claude.com/docs/en/hooks).

## Интерактивная работа

- `PreToolUse` / `PostToolUse` / `PostToolUseFailure` для Bash сравнивают состояние
  исходников до и после конкретного вызова (`tool_use_id`). Частичная запись
  неуспешной команды тоже учитывается.
- `PostToolUse` для файловых инструментов помечает изменения этой сессии;
  форматирование и линт изменённого файла остаются в `post-edit.sh`.
- `Stop` запускает `make check-fast`, только если сессия меняла проверяемые файлы.
  Старый dirty checkout и изменения другой сессии сами по себе не создают работу.
  Успех переиспользуется только для того же HEAD и содержимого source delta.
  Содержимое неизменных файлов повторно не читается: их связывает Git HEAD.
- Кеш находится вне репозитория: `$XDG_CACHE_HOME/bpmn-agent-checks` либо
  `~/.cache/bpmn-agent-checks`, отдельно для checkout и сессии. Команды, исходники,
  вывод проверок и секреты в нём не сохраняются. Общий lock не даёт двум Stop-хукам
  одновременно запускать проверку одного checkout. Изменения во время gate
  отменяют его переиспользование. Ошибка не превращается в успех кеша.
- Повторный Stop после той же ошибки не зацикливается; следующий обычный ход
  повторит проверку. При исправлении исходников она выполняется и в продолжении.
  Фоновые shell-задачи нужно завершить до финальной проверки: если Stop сообщает
  о них, проверка откладывается с сохранением pending-состояния.

Это быстрый feedback, не свидетельство полного gate, live runtime или состояния
установленных зависимостей. После смены окружения запускайте `make check-fast`
явно. У shell-вызова нельзя надёжно отличить его запись от совпавшей по времени
внешней записи; при совместной работе используйте отдельные worktree. Клиенты без
этих событий выполняют команды проверки вручную по scope изменения.

## Перед push и MR

`pre-push-check.py` читает реальные refs/OID из Git stdin, проверяет чистый checkout
публикуемого HEAD и классифицирует весь публикуемый delta. Lefthook передаёт stdin
через [use_stdin](https://lefthook.dev/configuration/use_stdin/).

- Только Markdown-документация, агентские инструкции/хуки, `.claude/settings.json`
  и `lefthook.yml`: изолированные тесты хуков, проверка JSON/wiring, ShellCheck
  и `lefthook validate`. Полные продуктовые
  проверки для такого изменения не нужны.
- Продукт, runtime, зависимости, контракты, смешанный или неизвестный scope:
  полный `make check`; перед MR — `make verify` согласно проектному workflow.
- Отсутствующий/некорректный stdin не означает пустой scope: выбирается полный gate.
  Push другой ревизии из текущего checkout отклоняется: проверять нужно именно
  публикуемый кандидат. Защиты веток и серверные обязательные проверки сохраняются.

Точечная команда (без запуска продукта):

```bash
python3 -B -m unittest discover -s scripts/agent-hooks/tests -p 'test_*.py'
shellcheck scripts/agent-hooks/post-edit.sh scripts/agent-hooks/stop-check.sh
./node_modules/.bin/lefthook validate
```
